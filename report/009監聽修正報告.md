結論：report/008listen.md 的主失效鏈路正確，但有幾個說法過度絕對；不能判定為「全篇完全正確」。

  - 三次連續解碼超時後，程式確實會：全監聽設備設為 OFFLINE → 呼叫 gateway.unregister_device() → 清除 HA Discovery retained config → 清空 listen adapters → 重建 executor。這是實際路徑。見 src/
    listen_master.py:216、src/main.py:348。

  - 因為一次 decode job 會依序處理「所有監聽 adapter」，其中一個 feed() 卡住，就能拖住整批；三次逾時後是整條監聽軌一起被卸載，不是只掉單台。
  - 熔斷後若 MQTT cleanup 成功，HA 實體會被刪除；若 MQTT 當時不可用，cleanup 發布失敗，則不能保證 HA 一定刪除。報告把這點寫成必然，過頭了。見 src/ha_manager.py:96。

  失效在哪種情況發生：

  1. adapter.feed() 真的超過 2 秒不返回：無窮迴圈、卡鎖、外部 I/O 永久阻塞。
  2. 系統極度卡頓，原本會結束的解碼卻連續三次超過 2 秒。
  3. 未來新增的 listen adapter 寫出上述行為。

  目前現場機率是 0：正式 profile/config.yaml:22 全是 mode: active，沒有 listen_driver，ListenMaster 根本不會建立。

  若未來啟用現有 jkbms 監聽：

  - 就 jkbms_adapter.feed() 的邏輯來看，所有 continue 前都會刪除資料、資料不足就 break，沒有外部網路、sleep 或鎖等待；由 parser 自身造成永久迴圈的機率可視為極低。見 adapters/jkbms_adapter.py:311。
  - 但「不可能觸發」仍太絕對：解析中仍可能寫日誌，且 CPU/容器停頓可使有限工作超過 2 秒。沒有歷史觸發紀錄與壓測資料，不能誠實給百分比。

  修法實際修正的是什麼：

  - V1.13 沒有修掉卡死或自動恢復；它修的是「關機時診斷計數錯誤」。現在只計入已經開始跑的 worker，不把排隊中、可取消的工作誤算為卡住。關機時會印 WARNING 提示仍在執行幾個 decode job。見 src/listen_master.py:139、
    src/listen_master.py:162。

  - 報告建議的 MAX_ITER=512，只是在 jkbms_adapter.feed() 防未來邏輯無窮迴圈；不能防鎖、外部 I/O 或 CPU 卡頓。而且上限到了清空 buffer 會丟資料，不是「無損修正」。現有 parser 已有前進保證，我不建議為這個假設風險現
    在加入它。

  - 現有熔斷則是「保護進程別無限生 thread」，代價是卸載監聽設備、HA 實體可能消失，且需重啟才重建監聽。

  另兩個需更正的報告文字：

  - 「之後永遠沒有任何日誌」不精確：正常收到 chunk 時確實不再有 decode/發布日誌，但 driver 斷線或核心例外仍會記錄。
  - 「Docker 必定等 10 秒 SIGKILL」不精確：compose 沒設定 stop_grace_period，通常會用 Docker 預設值，但實際等待時間取決於 Docker daemon／restart 指令參數。

› 正常來說每一偵約 160～180ms 所以發生2秒不回應表示卡死 ～應該是處理熔斷重啟的正確行為


• 對。以每幀 160–180ms 算，2 秒約等於連續漏掉 11–12 幀；正常 parser 不應碰到。連續三次才熔斷（約 6 秒以上）是合理的，避免把瞬時 CPU 抖動當卡死。

  但目前實作不是「熔斷後重啟監聽」，而是：

  熔斷 → executor 換新 → 卸載所有 listen 設備 → 清掉 HA Discovery → 監聽軌永久空轉

  所以它有熔斷，卻沒有恢復；必須人工重啟整個容器才能重新掛載設備。

  正確的自動處置應是：

  連續 3 次 >2s → 設備 OFFLINE，但保留 HA 實體 → 結束整個 gateway process → Docker restart policy 重啟 → 新進程清掉卡死 thread、重掛監聽、重發 Discovery

  這才是完整的「熔斷重啟」。目前 V1.13 只會告訴你關機有幾個 worker 還在跑，沒有改變上述恢復行為。

› 你分析另一個方案 當觸發熔斷 是否可以切斷adapter 後清空 buff重開 adapter ??我記得當初的設計是這樣的！


• 可以，但它只能處理「adapter 狀態壞掉」，不能處理真正觸發 2 秒熔斷的「adapter 卡住」。

  現行程式其實不是「切 adapter 後重開」；它是：

  timeout × 3
  → unregister 全部 listen device
  → 清 HA Discovery
  → 換新 ThreadPoolExecutor
  → adapters 已經是空的

  沒有重新建立 adapter。見 src/listen_master.py:231。

  兩種故障要分開看：

   失效類型                                清 buffer／重建 adapter 有效？                          2 秒熔斷後可用？
  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   buffer 殘包、假表頭、parser 狀態污染                              有效    不該等到熔斷；adapter 自己應立即 reset
  ──────────────────────────────────────  ────────────────────────────────  ────────────────────────────────────────
   feed() 無窮迴圈                                                   無效                    無效，舊 thread 還在跑
  ──────────────────────────────────────  ────────────────────────────────  ────────────────────────────────────────
   feed() 卡鎖、卡外部 I/O                                           無效                無效，Python 無法殺 thread
  ──────────────────────────────────────  ────────────────────────────────  ────────────────────────────────────────
   單次極慢但最後會返回                                          有限有效         不安全；舊呼叫仍可能改舊 instance

  關鍵點：timeout 只取消 await，取消不了已送進 ThreadPool 的 feed()。所以在熔斷時直接：

  切斷 adapter → clear buffer → new Adapter()

  舊 worker 還拿著舊 adapter，仍在跑。你雖可讓新 adapter 接新資料，但：

  - 舊 thread 沒消失，仍是洩漏。
  - 每熔斷一次至少殘留三個 worker。
  - 現行 decode job 是「一個 job 依序跑全部 adapters」，還不知道究竟是哪一台卡住，不能精準只重開某台。
  - 舊 adapter 若仍碰自己的 buffer，外部強行 buffer.clear() 是跨執行緒競態，不安全。

  因此正確分層是：

  正常 parser 異常／buffer 污染
  → adapter 自己清 buffer、重設 pending state、繼續監聽
  → 不進熔斷

  feed() 超過 2 秒 × 3
  → 視為 worker 不可回收
  → 不重開 adapter、不清 Discovery
  → 整個 process exit，由 Docker 重啟

  現有 jkbms_adapter 的 buffer 清理已在 parser 內處理：

  - 無表頭且累積超過 1024 bytes：清 buffer。
  - 假 JK / Modbus 表頭：刪除已確認的錯誤前綴。
  - 資料不足：保留殘包等待下一幀。

  見 adapters/jkbms_adapter.py:322。

  所以「重開 adapter」可以作為 parser 自我修復策略，但不應放在熔斷後當作 thread 卡死的解法。熔斷後仍應 process restart；否則只是看似恢復，實際上持續累積殭屍 thread。
