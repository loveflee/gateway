# Solis 43110 儲能控制 Bit 定義與安全寫入敵對式審查

**日期：** 2026-08-11
**性質：** 唯讀、敵對式、證據導向審查；沒有修改 production、profile、設定或 Docker，沒有重啟 Gateway，沒有對 43110（或任何實機暫存器）送出寫入。

## 人話結論

1. **43110 是 16-bit bitmask，不是單一「模式數字」。** 上游目前的 Storage Mode 實作會分開處理模式 bit 與獨立功能 bit；本機目前僅把它當 `uint16` 數字顯示與寫入。
2. **目前讀到的 `1` 是 `0x0001`，即只有 bit 0 為 1。** 依上游對 hybrid 的定義，這對應 Self-Use；但這只證明本機讀值，沒有取得本機機型的安全寫入實證，不能延伸宣稱所有功能狀態均已確認。
3. **`33` 不是純「自用」，`35` 也不是純「分時」。** `33 = bit 0 + bit 5`；`35 = bit 0 + bit 1 + bit 5`。依上游目前模型，35 是 Self-Use + TOU + 一個被保留的 grid-charge modifier；它不是 Peak Shaving（該模式 bit 為 11）。
4. **現有 number box 有誤導風險。** 它允許輸入 0–65535，標題卻只寫「33:自用 35:分時」，會隱藏其他已啟用或未知的 bit。
5. **直接寫整值有明確風險。** 本機 Adapter 對 `33` 實際組出 FC16 quantity=1，將整個 register 寫為 `0x0021`；原來的其他 bit（包括未知／韌體用途 bit）都會被清為 0。
6. **最安全的未來控制模型是「Storage Mode select + 受限 modifier switches」，並採 live read → 計算 → 整 word write → 完整回讀驗證。** 在雙 master 下仍不能保證沒有競態，因此必須偵測並回報衝突，不能盲目自動重試。現在不應啟用這類控制。
7. **現在不要修改。** 先保留現況為讀取／診斷用途；待取得本機 S6-EH1P6K 對各 bit 的已授權安全驗證條件後，再進行獨立、最小範圍施工。

**最終裁決：REDESIGN UI + WRITE PATH**
**是否值得為 43110 另外開一輪最小修改施工：YES**

## 2. 本機現況：43110 被建模為單一 uint16，且可整 word 覆寫

### 2.1 Profile 實際定義

本機地圖在 [solis_inverter_map.yaml](/root/py_ginlong/profile/solis_inverter_map.yaml:45) 以 FC03、count=1 讀 43110；同檔 [141–151 行](/root/py_ginlong/profile/solis_inverter_map.yaml:141) 把它定義成單一 `uint16` sensor，並設為 `write_fc: 16`。HA 端則是 [0–65535 的 number box](/root/py_ginlong/profile/solis_inverter_map.yaml:217)，名稱為「儲能模式 (33:自用 35:分時)」。

此 profile 沒有 bit 定義、`link_sensor`、mode conflict、dependency 或 unknown-bit preservation 規則。`map_validator.py` 只能確認 YAML／HA／基本數值格式，沒有能力判定一個 `uint16` setting 是 enum 還是 bitmask，也不會驗證 bit 寫入安全性。

### 2.2 本機實機唯讀觀察

[報告 025](/root/py_ginlong/report/025_10分鐘實機TX_RX解碼與地圖匹配觀察報告.md:23) 在 10 分鐘雙 master 觀察中，UID 1 得到 `set_storage_control: 1` 共 89 次，UID 4 亦得 `1` 共 52 次。這證明該次觀察下兩台的 raw word 是 `0x0001`；它**沒有**測試 bit 寫入、沒有證明所有 bit 的語意，也沒有證明兩台 firmware 完全相同。

### 2.3 實際編碼驗證（無 I/O）

在既有 `ginlong` container 內，只載入目前 profile 與 `GenericAdapter`，呼叫 `encode_write("set_storage_control", 33)` 與 `build_verify_read()`；未建立設備連線、未送 frame。結果為：

```text
write_33 = 01 10 A8 66 00 01 02 00 21 46 44
verify   = 01 03 A8 66 00 01 44 75
context  = {'type': 'verify', 'key': 'set_storage_control', 'read_fc': 3}
```

拆解 write request：UID=1、FC16、address=`0xA866`（43110）、quantity=1、byte-count=2、payload=`0x0021`（33）。因此這不是「寫 bit 5」或「選模式」；它是完整覆寫一個 16-bit holding register。

程式路徑亦直接佐證：`set_storage_control` 的 sensor 長度是 2 bytes，`GenericAdapter._resolve_fc16_codec()` 因而保留 legacy path；`encode_write()` 再以 `_build_fc16_request(..., struct.pack('>H', ...))` 建 FC16 count=1。見 [generic_adapter.py:155](/root/py_ginlong/adapters/generic_adapter.py:155) 與 [280–333 行](/root/py_ginlong/adapters/generic_adapter.py:280)。它沒有對 43110 特判、沒有先讀現值，也不支援 FC22。

靜態地圖檢查另已執行並 PASS：

```bash
docker exec ginlong python /app/src/map_validator.py /app/profile/solis_inverter_map.yaml
```

這只表示目前 YAML 的 validator 覆蓋範圍通過，**不**表示 43110 的模式／bit 語意或寫入安全通過。

## 3. 43110 真實資料模型判定

### 判定：bitmask（含互斥的 mode bits 與獨立 modifier bits）

上游最新 [select_sensors.py](https://github.com/Pho3niX90/solis_modbus/blob/master/custom_components/solis_modbus/sensor_data/select_sensors.py) 明確把 43110 定義為 `Storage Mode`，並宣告 mode-defining set 為 `{0, 1, 2, 4, 6, 11}`；切換模式時清除這些 mode bits，再 set 新模式所需組合。該檔特別說明 bits 3、5、7–10 是應保留的獨立 modifiers，而非 select 的單一 enum 值。

最新 [switch_sensors.py](https://github.com/Pho3niX90/solis_modbus/blob/master/custom_components/solis_modbus/sensor_data/switch_sensors.py) 為 43110 列出個別 bit switch，並附相依／衝突關係。上游的 [2026-07 Storage Mode redesign commit](https://github.com/Pho3niX90/solis_modbus/commit/9b0afff2787ff0214b75bcf926e76b94270d4ca6) 也明確記錄，舊模型若沒有清 bit 1，從 TOU 返回 Self-Use 會卡住，且錯誤組合可從 35 寫成 2082 而不是 SolisCloud 捕獲的 2080。

這是強於「單一 enum」的直接實作證據。因此，43110 的正確抽象不是純 enum，而是 **bitmask + mode conflict/dependency 規則**。至於每一個 bit 是否對本機 S6-EH1P6K firmware 完全可用，仍需要本機安全驗證。

### 可確認的 bit 表

| bit | mask | 上游名稱／關係 | 讀取時 bit=1 | 讀取時 bit=0 | 本機可否安全寫入的結論 |
| ---: | ---: | --- | --- | --- | --- |
| 0 | `0x0001` | Self-Use Mode；與 2、6、11 衝突 | Self-Use 選擇存在 | 未選 Self-Use | **未驗證**；本機只讀到此 bit=1 |
| 1 | `0x0002` | Time of Use；需要 0 或 6 | TOU 選擇存在 | TOU 未設 | **未驗證** |
| 2 | `0x0004` | Off-Grid Mode；與 0、1、4、6、11 衝突 | Off-grid 選擇存在 | Off-grid 未設 | **未驗證** |
| 3 | `0x0008` | Battery Wakeup Switch；獨立 modifier | 上游命名功能已設 | bit 未設 | **未驗證** |
| 4 | `0x0010` | Reserve/Backup；需要 0、與 2／11 衝突 | Reserve modifier 已設 | 未設 | **未驗證** |
| 5 | `0x0020` | Allow Grid to Charge the Battery；獨立 modifier | 上游 field captures 解讀為「允許」 | 該 modifier 未設 | **有文件／field polarity 矛盾，未驗證** |
| 6 | `0x0040` | Feed-In Priority；與 0、11 衝突 | Feed-in 選擇存在 | 未選 | **未驗證** |
| 7 | `0x0080` | Batt OVC；獨立 modifier | 上游命名 bit 已設 | bit 未設 | **語意／寫入未驗證** |
| 8 | `0x0100` | Battery Forcecharge Peakshaving；獨立 modifier | 上游命名 bit 已設 | bit 未設 | **語意／寫入未驗證** |
| 9 | `0x0200` | Battery Current Correction；獨立 modifier | 上游命名 bit 已設 | bit 未設 | **語意／寫入未驗證** |
| 10 | `0x0400` | Battery Healing Mode；獨立 modifier | 上游命名 bit 已設 | bit 未設 | **語意／寫入未驗證** |
| 11 | `0x0800` | Peak Shaving；與 0、1、2、4、6 衝突 | Peak Shaving 選擇存在 | 未選 | **未驗證** |
| 12–15 | `0x1000`–`0x8000` | **UNKNOWN / UNVERIFIED** | 不可賦予意義 | 不可賦予意義 | 不可碰觸，必須保留 |

「bit=1／0」在表中只表示 bit 有設／未設；除 bit 5 以外，不能被誤讀成所有功能必然是簡單 enable／disable。bit 5 尤其有不一致證據：上游註解指出 Appendix 的字面說法為 `0=Allow, 1=Not allow`，但其 SolisCloud field captures 的組合值卻顯示相反極性；上游因此採「bit set = allow」。這個矛盾本身就是本機不得直接提供 switch 的理由。

## 4. 值 1、33、35 的正確拆解

| 十進位 | hex | 16-bit binary | set bits | 可負責任的解讀 |
| ---: | --- | --- | --- | --- |
| 1 | `0x0001` | `0000 0000 0000 0001` | 0 | 本機實測值。依上游 hybrid mapping：Self-Use；其餘已知 bit 1–11 當時均未設。 |
| 33 | `0x0021` | `0000 0000 0010 0001` | 0、5 | 上游模型：Self-Use + grid-charge modifier。稱作「純自用」會遺漏 bit 5。 |
| 35 | `0x0023` | `0000 0000 0010 0011` | 0、1、5 | 上游模型：Self-Use + TOU + grid-charge modifier。稱作「純分時」會遺漏 bit 0、5。 |

因此目前 profile 的「33:自用、35:分時」是過度簡化：

- 若「分時」指 TOU，35 內確有 bit 1，但它仍不是只開 TOU。
- 35 並非目前上游 bit model 下的 Peak Shaving；Peak Shaving 是 bit 11，典型 field-capture 值是 `2048` 或保留 bit 5 時的 `2080`。
- [Issue #413](https://github.com/Pho3niX90/solis_modbus/issues/413) 的使用者曾在 **S6-EA1P4.6K-L** 回報「33=Self-Use、35=Peak Shaving」。這是特定機型的使用者敘述，後續上游實作／capture table 已以 bit model 處理；它不能覆蓋本機 S6-EH1P6K，也不能當作 profile raw number label 的唯一依據。

## 5. 上游已發生的「寫一個 bit，清掉其他 bit」事件

這不是純理論風險。上游 [issue #402](https://github.com/Pho3niX90/solis_modbus/issues/402) 記錄，在 integration reload 後快取為空時，對 43110 個別 bit 的 read-modify-write 從 0 開始，導致其他 bit 被清除；回報影響 bit 3、4、5、7–11。

上游已合併的 [commit `875ff52`](https://github.com/Pho3niX90/solis_modbus/commit/875ff523efd6ce62ca7b9b4d56b34898bdb51f82) 的 commit message 與目前 [solis_select_entity.py](https://github.com/Pho3niX90/solis_modbus/blob/master/custom_components/solis_modbus/sensors/solis_select_entity.py) 的 120–158 行一致：快取為空時先從 inverter 讀 live value；讀取失敗則跳過寫入，避免把未知 bits 當成 0。然後在記憶體內清除衝突 bit、加入 dependency、設定目標 bit，最後仍以「整個 holding register」寫回。

本機的直接整值寫法比該舊 bug 更直接：它完全沒有讀取／保存動作。當目前 word 不是正好 0 時，任何輸入 33／35 都可能清除原本 bit 3、4、7–15，且對 bit 5 的值亦是使用者手動硬編碼，並不保留既有狀態。

## 6. 目前本機寫入／ACK／verify 的邊界

`BusMasterScheduler._process_write()` 先呼叫 `encode_write()` 與 `build_verify_read()`，再於本 Gateway 的 `bus_lock` 內執行「write → ACK → verify read」。見 [bus_master.py:220](/root/py_ginlong/src/bus_master.py:220)。它沒有 pre-read，也沒有保留 non-target bits 的比較。

`bus_lock` 只序列化本 Gateway 的 coroutine；無法鎖住共線的原廠 WiFi master。因此即使未來在此流程加了 RMW，本 Gateway 仍會面對「read 完後、write 前，原廠 master 改了 43110」的 lost update 風險。

目前 `Driver.write()` 對 FC05/06/15/16 會檢查 RTU UID、FC、CRC、長度與 echo；見 [driver.py:289](/root/py_ginlong/src/driver.py:289)。**FC22 不在該清單中**，若今天任意塞進 FC22 payload，會落到 blind-ACK return，而不是現有安全 ACK 合約。這使 FC22 目前不是可直接採用的捷徑。

## 7. 三種寫入方案比較

### A. 直接整值寫入，例如 `43110 = 33`

**優點：** 現在已能發送；最少程式碼；現有 FC16 ACK 可以驗證 address／quantity，後續 FC03 可回讀整 word。

**風險：** 寫入者必須知道完整 16-bit 真值。任何未表達的 modifier、未知 bit 或 firmware bit 都被清除；UI number box 允許的任何數字都可能形成不合法組合。雙 master 又使「使用者看到的值」很可能已在寫入時過期。

**安全結論：** 不安全作為 bit 控制。只有在 OEM 明確定義「這是純 enum」、使用者持有完整的型號／firmware 專屬 word、並且可接受覆寫所有 bits 時才可能使用；現有證據不滿足這些條件。

### B. Read-Modify-Write（推薦的未來基礎）

流程應是：

```text
讀取 live 43110
→ 驗證目前 word 與允許的 bit model
→ 僅清除目標 mode 的衝突 bits／設定必要 bits，保留其他 bits
→ FC16（或 FC06）寫回完整 word
→ ACK
→ 讀回完整 43110
→ 驗證目標 bits 與「應保留 bits」；偵測並報告競態衝突
```

**適配本機架構：** GenericAdapter 目前是純編碼／解碼，不能自行做 I/O；真正 RMW transaction 必然需要 orchestration。若未來要做，須先提出最小 contract 設計並證明是否需要一個受限的 BusMaster transaction helper。不能把 RMW 偷塞在 `encode_write()`，因為那裡沒有 live read。這意味著「只改 profile」不可能安全完成。

**雙 master 競態：** 本機 `bus_lock` 不能涵蓋原廠 WiFi master。read 與 write 間若 WiFi master 寫入，Gateway 會以過期 word 覆蓋它，形成 lost update；write 後若 WiFi 又寫，verify 可能看到非目標 bits 改變。立即 reread 可縮小窗口但無法消除它；標準 Modbus 沒有可對此設備已證實的 compare-and-swap。

**必要行為：**

- live read 失敗、word 含無法理解的受保護位元、或 mode 組合不合法：拒絕寫入。
- 把 read value、target mask、computed word、ACK、verify word 寫入可審計的 transaction-level diagnostic（避免正常 INFO 洪水）。
- verify 必須同時確認目標 bit 與 pre-read 時本應保留的 non-target bits；若不一致，標記 **conflict / NOT APPLIED SAFELY**。
- 不要自動反覆重試 RMW 去「贏過」原廠 master；那會加劇兩個 master 的控制競爭。應把衝突交給使用者／排程重新發起。

**安全結論：** 在先取得本機 bit／firmware 白名單後，這是最實際的方案；但不是只改 GenericAdapter 就能完整落地。

### C. FC22 Mask Write Register

[Modbus Application Protocol Specification V1.1b3 §6.16](https://www.modbus.org/file/secure/modbusprotocolspecification.pdf) 定義 FC22：以 AND mask、OR mask 與 device 當前 register contents 計算結果，理論上可 set／clear 個別 bits，避免 client-side read→write 的主要窗口。

**理論優點：** 在 server 支援並正確實作時，mask 計算可於單一 Modbus transaction 套用目前 word；比 client RMW 更接近原子操作。

**目前不能採用的原因：**

1. 沒有本機 Solis S6-EH1P6K／此 firmware 支援 FC22 的設備證據；本輪禁止探測性寫入。
2. `GenericAdapter` 不組 FC22；`Driver.write()` 也沒有 FC22 的 UID／FC／mask echo／Exception ACK guard。
3. 官方規格本身提醒 register contents 仍可隨 controller 的 user logic 改變；FC22 不是對外部 WiFi master 的全域鎖。
4. 為一個未證實設備能力擴充 Adapter + Driver + test contract，超過本輪最小且高確定性的安全修正範圍。

**安全結論：** 現在不導入、不試寫。若日後獲得該型號 OEM 文件與可回復的授權測試設備，才可另案做 FC22 capability probe、完整 ACK／Exception tests 與實機 verify。

## 8. Home Assistant UI 模型評估

| UI | 優點 | 問題 | 結論 |
| --- | --- | --- | --- |
| 單一 number（現況） | 最少開發，raw word 可診斷 | 把 bitmask 偽裝 enum；0–65535 允許任意不合法組合；整值寫會清 bit | **不適合控制**；最多保留為 read-only diagnostics |
| 單一 select | 可呈現互斥的核心 Storage Mode | 若每個選項直接寫 raw 數值，仍破壞 modifier／unknown bits | 核心模式層合理，但必須建在安全 RMW 上 |
| 多個 switch | 可呈現個別 bit | 容易讓互斥／相依 bit 被使用者組成危險組合；bit 5 polarity 與 7–10 的本機語意未確認 | 不宜直接全面暴露 |
| **select + 受限 switches** | 把 mode bits 與獨立 modifiers 分開，最接近實際 bitmask | 需要明確的 bit 白名單、conflict/dependency 與 RMW conflict handling | **本機驗證完成後的推薦模型** |

未來 UI 的保守設計應是：

1. 先新增 raw 43110 的 **read-only diagnostic**（值與 set-bits），不讓未知狀態被藏起來。
2. 以 select 表示經本機驗證的 Storage Mode；選擇時只管理 `{0,1,2,4,6,11}`，並保留其他 bit。
3. 只有在本機安全驗證過的 modifier 才新增 switch。bit 3、5、7–10 不可因上游名稱就全部曝光；bit 5 應先解決 polarity 矛盾。
4. 未知 bits 12–15 永遠保留、顯示為 unknown，而非清零。

- [commit `9b0afff`](https://github.com/Pho3niX90/solis_modbus/commit/9b0afff2787ff0214b75bcf926e76b94270d4ca6) 將 Work Mode 重做為 Storage Mode，並以 `{0,1,2,4,6,11}` 為 mode set、保留 3/5/7–10；修正 TOU 卡住及 2082/2080 的錯誤組合。
- #413 的來源設備是 S6-EA1P4.6K-L；#82 的討論涉及不同的 S6-EH3P15K-H。兩者皆非本機 S6-EH1P6K。因此它們能證明「不同 Solis hybrid 版本確有差異／bitmask 問題」，不能取代本機機型與 firmware 的寫入驗證。

| 上游版本／時期 | 43110 行為差異 | 對本機審查的意義 |
| --- | --- | --- |
| `875ff52` 以前 | cache 空時的 bit RMW 會由 0 起算，可能把非目標 bits 歸零。 | 不能以「採 RMW」三字就宣稱安全；live read failure 必須拒絕寫入。 |
| `875ff52` 起 | cold cache 時先讀 inverter 的 live word；讀失敗即跳過寫入。 | 是未來設計的最低防線，不是可直接複製到本機的完整雙 master 解法。 |
| `9b0afff` 以前的 Work Mode select | mode conflict 清除不完整，TOU bit 可能殘留，Peak Shaving 可得到錯誤 `2082`。 | raw `33`／`35` 不能被視為跨版本穩定 enum。 |
| `9b0afff` 至目前 `bbdd1f2` | Storage Mode 以 mode set `{0,1,2,4,6,11}` 重算，保留 3/5/7–10。 | 本報告的 bitmask 模型依據；仍須以本機機型／firmware 驗證。 |

## 10. 若另開施工輪，最低限度的安全驗證計畫

先取得使用者明確授權與本機機型／firmware／可復原測試時段，再依序：

1. **唯讀基線：** 長時間記錄 43110 raw value、set bits、SolisCloud／原廠 App 操作前後差異，且與每台 UID 分開。不得用猜測的暫存器寫入取代此步。
2. **isolated bit algebra：** 對 `1/3/17/33/35/49/51/64/96/98/2048/2080`、unknown high bits、衝突組合，驗證 mode clear／dependency set／modifier preservation。另測 live-read failure、invalid bit、未知 bit、verify mismatch。
3. **transaction regression：** 既有 FC05/06/16 request、ACK、verify、timeout／offline state、traffic log、poll rotation 都必須 byte/語意一致。RMW conflict 不可被誤報為 physical failure 或自動與 WiFi master爭寫。
4. **Adapter／BusMaster boundary review：** 證明 RMW 最小 contract 位置；若無法在既有 write transaction 中安全引入，停止而非擴大修改。不得修改 Driver／BusMaster，除非新審查先證明無法完成並獲重授權。
5. **實機最小測試：** 只在使用者指定、已知安全且可復原的條件下，對一個已被原廠 UI 先確認的 bit 做一次 RMW；擷取 write ACK 與完整 verify raw word，再由人確認原廠 UI、HA state、SolisCloud／WiFi master 沒有意外改變。沒有此條件即標記 `NOT TESTED`。
6. **FC22：** 另案；先有 OEM／設備支援證據與完整 Driver ACK test，不能把它混進 RMW 第一輪。

## 11. 本輪未做與限制

- 沒有寫 43110、沒有 probe FC22、沒有改 HA entity、profile、Adapter、Driver、BusMaster、map validator、Docker 或設定。
- 沒有把原廠 WiFi master 與 Gateway 的雙 master collision 視為 defect；本報告只指出新的控制寫入若忽略它會造成 lost update。
- 沒有聲稱本機 S6-EH1P6K 的 bit 3–15 已被 OEM 或實機寫入驗證。
- 沒有把 SolisCloud field capture、GitHub issue 敘述或上游 code 當作本機設備寫入許可。

## 12. 最終裁決

**REDESIGN UI + WRITE PATH**

理由：43110 已有足夠上游實作與已修 bug 證據顯示它是含 mode／modifier 的 bitmask；現況 raw number + whole-word FC16 寫入既有清除其他 bits 的直接風險。可是本機機型／firmware 尚缺安全寫入證據、且現場存在不可被本 Gateway lock 管控的原廠 WiFi master，所以不能直接施工或先改 UI 來掩蓋 write path 問題。

**是否值得為 43110 另外開一輪最小修改施工：YES。** 前提是先取得本機 S6-EH1P6K 的受控 read baseline、授權的可回復測試條件，以及針對雙 master conflict 的明確產品行為；否則維持目前僅讀／診斷用途。
