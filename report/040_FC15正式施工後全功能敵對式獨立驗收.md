| 5 | **錯 Protocol ID** | 拒絕 | `True` | **FAIL** |
| 6 | **錯 UID** | 拒絕 | `True` | **FAIL** |

**11/11 種畸形與 exception 回應全部被判定為「寫入成功」。**

### 根因

`src/driver.py::write()` 的守衛：

```python
if (len(payload) < 8
        or payload[1] not in (5, 6, 15, 16)
        or not _has_valid_modbus_crc(payload)):
    return True
```

MBAP 封包**無 RTU CRC**，`_has_valid_modbus_crc()` 必然失敗 → 直接 `return True` 盲收。`modbus_tcp_driver.py::write()` 只是 `return await super().write(payload)`，未加任何 MBAP 驗證。

### 這不是 FC15 引入的問題 —— 它現在就在影響現場

`profile/config.yaml` 中 **UID 1（溫濕度）與 UID 3（8 路繼電器）都是 `adapter: tcp`**。這代表：

> **本機今天所有的寫入，driver 層都不做任何 ACK 驗證。設備即使明確回報 exception（「我拒絕這個指令」），Gateway 也會判定寫入成功。**

目前唯一的安全網是 `bus_master` 的 FC01/FC03 回讀驗證。這條防線是有效的，但它是**第二道**防線在獨自承擔全部責任 —— 且第 5 節顯示第二道防線本身也有 fail-open 缺口。

**第九節判定：FAIL。**

## 5. 第五／六節：資料流黑洞搜尋 — **FOUND（3 個）**

### 黑洞 D 🚨 `group state 無匹配 → None → 判定寫入成功`（已實跑 production 重現）

實跑 production `BusMasterScheduler._process_write()`，adapter 對群組 key 回傳 `None`：

```
[PASS] 🚨 群組反查回 None → BusMaster 判定寫入成功並 publish（黑洞 D 仍開啟）  publish 次數=1（期望修好後為 0）
[PASS] bus_master.py 仍含 `decoded[key] is None → 視為成功` 後門
```

`src/bus_master.py::_process_write()`：

```python
if decoded.get(key) is None:
    logger.warning(f"[{uid}] 寫入驗證回讀 key={key} 值為 None (可能不支援該資料型別)，無法比對，視為成功")
    ha_mgr.publish_state(decoded)
    self._record_success(uid)
    return
```

**後果：** 群組實際落在未命名／禁止組合（例如 ATS 雙路同時導通）時，自然的 adapter 實作會回 `None` → 系統回報「寫入驗證成功」並把該狀態發布給 HA。**這是 fail-open，且落在有實體後果的應用上。**

### 黑洞 B `FC15 ACK 錯誤但被當成功`

即第 4 節。11 種畸形 ACK 全被接受，包含 `0x8F/01` illegal-function exception。**設備明確說「我不支援 FC15」，Gateway 判定成功。**

### 黑洞 E 潛在 `partial verify`

`_values_equal()` 是**單一純量**比較：

```python
def _values_equal(a, b, tolerance: float = 0.01) -> bool:
    if type(a) == type(b) and isinstance(a, (int, str)):
        return a == b
```

BusMaster 只做 `_values_equal(decoded.get(key), value)`，**不會逐 bit 比對**。多 bit verify 的正確性 100% 押在 adapter 反查邏輯上，BusMaster 無第二道防線。反查若稍寬鬆（部分匹配／就近匹配）即產生 partial verify 假 PASS。

實測 exact-compare 參考實作（**非 production**）：

```
[PASS] exact vector 比對：完全相符才回命名狀態
[PASS] 單 bit flip ['OFF','OFF','ON','ON'] 必須 FAIL verify
[PASS] 單 bit flip ['ON','ON','ON','ON']   必須 FAIL verify
[PASS] 單 bit flip ['ON','OFF','OFF','ON'] 必須 FAIL verify
[PASS] 單 bit flip ['ON','OFF','ON','OFF'] 必須 FAIL verify
[NOT-TESTED] 上述 exact-compare 為本檔參考實作，非 production
```

→ 目標 `[ON,OFF,ON,ON]` 的四種單 bit flip 全部正確判 FAIL，**證明 exact-compare 契約可行**，但 production 無此邏輯可測。

### 已驗證**不成立**的黑洞

- **黑洞 A**（command 收到但無 TX/error/log）：`_process_write` 各例外分支皆有 `logger.warning`／`logger.exception` + retry，未發現靜默路徑。
- **黑洞 F**（exception 被 catch 後無 retry/failure）：全部 `except` 分支皆 `physical_fault_count += 1` + `continue`，耗盡後 `_record_failure`。
- **黑洞 G**（pending_writes 覆蓋無 log）：達上限 200 時有明確 warning；同 key 覆蓋為既有 last-write-wins 設計，非新增缺陷。

### sentinel 方案有效性驗證

```
[PASS] sentinel __UNMATCHED__ → 不 publish、進 retry（fail-closed 可行）  publish 次數=0
```

日誌實錄：

```
[3] 回讀值不符 key=ats_group 寫入=path_a 回讀=__UNMATCHED__ (嘗試 1/3)
[3] 回讀值不符 key=ats_group 寫入=path_a 回讀=__UNMATCHED__ (嘗試 2/3)
[3] 回讀值不符 key=ats_group 寫入=path_a 回讀=__UNMATCHED__ (嘗試 3/3)
```

→ **038 提出、039 驗證的 sentinel 方案確實可在不改 BusMaster 的前提下 fail-closed。** 零 publish、正常 retry、留下明確 mismatch log。但**這只是可行性證明，production 未採用。**

| exception（現況 native TCP） | **誤判為是** 🚨 | 無 | +1 | 不變 | ONLINE | 不變 |
| timeout | 否 | 3 次 | 不變 | +1 | 連續 5 次後 OFFLINE | 轉 unavailable |
| malformed ACK（現況 native TCP） | **誤判為是** 🚨 | 無 | +1 | 不變 | ONLINE | 不變 |

**關鍵區分（039 第 7 點描述正確，此處確認）：**

- `__UNMATCHED__` 耗盡重試後仍呼叫 `_record_success()` 保持 ONLINE —— 這是 **transport health 記帳**（總線通得到、設備有回應），**不是 command verified success**（零 publish、留下明確 mismatch log）。此區分正確，**不判 FAIL**。
- 但 exception 與 malformed ACK 兩列 🚨 是**真正的混淆**：設備明確拒絕／回應畸形，卻被記為 command 成功並 publish。**這才是 fail-open。**

**第二十一節判定：FAIL**（因 exception／malformed ACK 兩列混淆了 transport healthy 與 command verified success）。

## 12. 第二十二節：Retry 原子性 — PASS（未被 FC15 改動）

`_process_write()` 的臨界區：

```
async with self.bus_lock:
    Write-TX → driver.write(ACK) → Verify-TX → driver.read(Verify-RX)
```

- 單次 attempt 內 write + ACK + verify 全在同一 `bus_lock`，本 Gateway 其他 poll/write 不得插入 — **PASS**
- `for attempt in range(...)` 在 `bus_lock` **外層** → retry 之間鎖會釋放，其他操作可插入 — **如實記錄，不誇大為跨 retry 的 global atomic transaction**
- scheduler 未因 FC15 改動（雜湊相同）— **PASS**
