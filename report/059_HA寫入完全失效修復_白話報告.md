## 最重要的一件事

**你在 HA 上對這四台 Solis 做的任何設定，從 8 月 8 日起就完全沒有生效過。**

不是偶爾失敗，是 **100% 失敗**，而且封包**連設備都沒到** —— 在網關內部就被自己擋下來了。

更糟的是日誌會說謊：它把這個格式衝突記成「設備 Timeout」，所以看起來像是匯流排或設備有問題，實際上是網關自己的程式擋的。

### 這是我造成的

8 月 8 日我提交了一批 FC15／FC16 的功能（commit `e618ab7`），裡面包含一個「原生 Modbus TCP 嚴格驗證」的改動。

問題是：**你的四台 Solis 用的不是原生 Modbus TCP。**

用個比喻：
- 你的設定是「用 TCP 網路當管線，裡面跑的是 RS485 的信封格式」（業界叫 RTU-over-TCP，因為中間有一台串口伺服器）
- 那個改動加上的檢查，卻是「拆開信封，第 3、4 個字必須是 0」—— 那是**另一種**信封格式（原生 Modbus TCP）的規則
- RS485 信封的第 3、4 個字是**暫存器位址**，不可能是 0

於是每一封信都被自己的收發室退件，一封都沒寄出去。

**我三天前才寫過一份報告（020）專門講這兩種信封格式的差別**，然後審查那個改動時沒把兩件事連起來，還在 AGENTS.md 裡把它記成新功能。這是我的疏失。

### 實際證據

`set_switch`（逆變器總開關）產生的封包：

```
01 10 A7 FF 00 01 02 00 01 A5 55
      ^^^^^ 這兩個 byte 是暫存器位址 43007，被當成「信封格式編號」
→ DriverTimeoutError: MBAP Protocol ID mismatch: 43007
→ 封包在送出前就被拒絕，一個 byte 都沒上線
```

### 怎麼修的

讓收發室**先看信封上有沒有 RS485 的封緘（CRC 校驗碼）**：
- 有 → 這是 RS485 信封，交給原本就正確的 RS485 檢查流程
- 沒有 → 這是原生 Modbus TCP 信封，走新加的嚴格檢查

這個判別方式**不是新發明的** —— 三天前我在另一個驅動檔（`driver.py`）用的就是同一招，這次只是補到漏掉的那個檔案。

**驗證（4 項全過）**

| 測試 | 結果 |
|---|---|
| Solis 的 `set_switch` 封包能送出且 ACK 驗證通過 | ✅ |
| 別台設備的 ACK 仍被拒絕（保護沒被削弱） | ✅ |
| 原生 Modbus TCP 設備（繼電器）行為逐字不變 | ✅ |
| 壞掉的 MBAP 封包仍被拒絕 | ✅ |

**⚠️ 一個必須說清楚的限制**

我**沒有對真實逆變器發送任何寫入**。上面的驗證是用「假設備」在程式層面完成的 —— 證明封包現在會被送出、ACK 檢查邏輯正確，但**沒有證明真實的 Solis 會接受它**。

依你「沒有安全實機暫存器就不准亂寫」的規矩，這一步要你在場時才做。

**建議的驗收方式**：在 HA 上改一個安全的設定（例如充電電流限制，改成目前值 ±1），看它是否在幾秒內生效並保持住。如果還是彈回去，那就是另一個問題。

## 其他三項修正

### 修正 2：我上一輪漏改了一個地方

上一輪（report 057）我把「HA 確認收到才更新自己的帳」這個規則套到三個地方，**漏了第四個** —— 監聽模式的「強制拔管」路徑（實體斷線或解碼熔斷時）。

**漏掉的後果**：那個地方會先把本地狀態改成離線、再通知 HA。如果通知寄失敗，我的撤回機制會把「上次告訴 HA 的值」還原成「在線」，而本地已經是「離線」了 —— **兩本帳分叉，而且誰也不會再補送**。

然後 MQTT 一恢復連線，網關會依那個舊紀錄**重新宣告這台設備在線** —— 明明它已經斷線了。

**改完**：通知成功才更新本地狀態。失敗就維持原狀，讓下一輪離線檢查重試。

還有一個細節：失敗時**不更新「最後看到封包的時間」**。如果更新了，重試會被推遲整整 60 秒。

**現行部署沒有監聽設備，所以這條不影響你現在的系統。**

### 修正 3：監聽模式重連後可能長期沒有數值

**原本會怎樣**

狀態資料是「寄平信」（QoS0，不保留），broker 重啟或斷線期間發出去的一律消失。

- **主動輪詢模式**（你現在的四台）：每一輪都重送整包資料，最多 6 秒就自己補回來 —— 沒問題
- **監聽模式**：只在「數值有變動」時才發布。如果設備一直送相同數值，HA 會停在空白或舊值，**直到某個數值再次改變為止**

期間 HA 顯示設備在線、沒有任何錯誤日誌。

**改完**：MQTT 重連時，把整包快取補送一次。

**風險**：這是新增的發布動作。呼叫時機只有「MQTT 重連」，而且每台之間已經有 2 秒間隔，不會造成洪泛。

### 修正 4：USB 模式會吞掉設備的拒絕

**原本會怎樣**

USB 驅動送出寫入後，**收到回應就直接丟掉，一律回報成功**。

所以設備如果明確回「我拒絕這個寫入」（例如寫入值超出範圍、寫到唯讀暫存器），網關完全不知道。如果接下來的回讀又剛好讀到目標值（**重複寫入目前的值最容易命中**），就會被記成「寫入驗證成功」—— 而設備一個 bit 都沒改。

**改完**：跟另外兩個驅動用同一套 ACK 檢查。設備明確拒絕就回報拒絕。

**保留了盲收語意**：只有「格式良好的 RS485 寫入請求」才套用這套檢查，其他任何非標準協定的 USB 設備行為完全不變。

**你現在沒有 USB 設備，這條是預防性的。**

## 查到但沒動的一個既有問題

重啟後我看到日誌裡有「輪詢解碼**未預期**例外」加上整串 traceback。追下去發現：

**程式裡有兩個同名但不同的例外類別。**

```
bus_master.py           class DataDecodeError      ← 排程器自己定義的
generic_adapter.py      class DataDecodeError      ← 解碼器定義的
是同一個嗎 → False
```

排程器寫的 `except DataDecodeError`（預期中的解碼失敗，印一行警告）**永遠攔不到**解碼器丟出來的那個，所以每次都掉到「未預期例外」，印出完整 traceback 並記為 ERROR。

**這就是你先前看到「3 分鐘 213 行 traceback」的來源** —— 那不是 213 次崩潰，是 213 次正常的雙 master 撞包，只是被誤分類成崩潰。

**功能上完全無害** —— 兩條分支做的事一模一樣（都記一次通訊失敗）。純粹是日誌分類與可讀性問題。

**我沒有修**，因為：
1. 不在這次授權範圍內
2. 修法有取捨：排程器**不應該**去 import 特定 adapter 的東西（那會破壞外掛的邊界），所以要嘛用類別名稱比對（有點取巧），要嘛把例外搬到共用模組（那是重構，不是最小修正）

**建議**：值得修，因為它讓日誌變得幾乎無法閱讀，也讓已知的環境噪音看起來像系統在崩潰。但要你決定用哪種修法。
