# 022｜效能基準與無損候選最佳化報告

日期：2026-08-09  
範圍：`/root/py_ginlong`；僅讀取生產目錄，測試在隔離的 `test/perf_baseline/` 進行。  
結論：已建立可重跑基準與「輸出／記錄／協定語意等價」的測試候選；**未修改** `src/`、`adapters/`、`profile/` 或任何運行中服務。

## 結論先行

最值得優先處理的端到端問題是「資料完整輪替時間」，不是 Python CPU：目前四台 active RTU 設備各以 `poll_interval: 15` 輪詢，而每張 Solis map 有 15 個 `read_commands`，故同一設備一個點位的完整輪替約為 **225 秒**（15 × 15 秒）。這是設定的可觀測輪詢節奏；調快它會改變總線負載與對外時序，未經硬體驗證與批准不得變更。

在不改變任何封包、解碼值、警告或拒絕語意的前提下，最有價值的 CPU 候選是：

1. 將 CRC-16/MODBUS 的逐位元計算換成等價、不可變的查表。
2. 在已通過 `map_validator` 的 profile 上，依 `command_id` 預索引 sensor，保持該 command 內原有順序。

在真實 `solis_inverter_map.yaml` 的隔離基準中，這組候選使單次 decode 中位數由 **34.724µs 降為 12.166µs，改善 64.96%**。它降低 CPU 消耗，但不會縮短目前 225 秒的資料完整輪替；因此它是低風險的候選修正，而不是替代輪詢設計決策。

## 不可碰的穩定性邊界

雙 Master 結構及其地獄式穩定測試依題意是刻意非常態測試，**不列為缺失**。本次沒有建議或實作降低下列保護：

| 邊界 | 量測／設定 | 不修改原因 |
| --- | ---: | --- |
| 空緩衝清理 | 50.193ms（本機 loopback 中位數） | 清除殘幀與雜訊；跳過會改變雙 Master／雜訊競態的處理時機。 |
| 幀尾 idle 判斷 | `idle_timeout: 0.1s` | TCP/串口碎包完整性界線，縮短可能截斷有效幀。 |
| RS485 幀間距 | 生產設定 `inter_frame_delay: 0.35s` | 硬體 turnaround 保護，禁止為吞吐率縮短。 |
| 同 UID／FC 錯 quantity 拒絕 | 保持原始 `DataDecodeError` | 防止雙 Master 造成的合法 CRC 舊幀被誤認。 |

以立即回應、保持連線的 127.0.0.1 假 Modbus 裝置量測，並強制 `inter_frame_delay=0` 後，單筆乾淨讀取仍為 **150.663ms** 中位數，正好由約 50ms 空緩衝等待與 100ms 幀尾 idle 判斷主導。這是有意的協定保護，並非可未經批准移除的效能缺陷。

## 基準工作負載與結果

使用的實際 profile 為 `solis_inverter_map.yaml`：49 sensors、15 read commands、5 writable settings。每個樣本 75,000 次 decode，9 個樣本；Python 3.13.5、PyYAML 6.0.3。

| 指標 | 基線 | 候選 | 改善 |
| --- | ---: | ---: | ---: |
| 單次 decode 中位數 | 34.724µs | 12.166µs | 64.96% |
| 單次 decode 最小值 | 34.545µs | 12.051µs | — |
| 單次 decode 最大值 | 35.167µs | 12.395µs | — |
| 每樣本操作數 | 75,000 | 75,000 | 相同 |
| 解碼結果 key 總數 | 260,000 | 260,000 | 相同 |

基線 `cProfile`（15,000 decode）顯示最重路徑為 `decode()`／`_extract_data()`；其中 `calc_crc16()` 有 30,000 次呼叫、累積 0.392s，且全量掃描 sensor 造成 1,134,000 次 `dict.get()`。這正是 CRC 查表與 command 索引的量測依據。

## 等價性驗證

候選在隔離測試中全部通過：

- 289 個 CRC 向量（空、全部單位元組值與多組 2～1024 bytes 向量）輸出完全一致。
- 真實 profile 的 15 個 read commands，正常幀與前後雜訊幀的解碼輸出 hash 全數一致。
- 同 UID／同 FC、錯誤 quantity 的拒絕型別與文字完全一致：`DataDecodeError: Response quantity mismatch: expected 8 count (16 bytes), received 2 bytes`。
- 原本 offset 越界的既有 warning 文字與解碼輸出完全一致。
- 5 個 writable settings 的 `encode_write()` 封包與 `build_verify_read()` 回傳完全一致。
- 隔離副本的 `map_validator` 已通過實際 Solis profile。

## 端到端瓶頸排序

1. **資料新鮮度／完整輪替（225 秒）**：由每設備 15 秒輪詢及 15 命令 round-robin 決定。若業務需要更快數據，必須先取得批准，再以實體總線測試調整 cadence 或讀取分組；這會改變外部時序，不能視為無損微調。
2. **協定 I/O 保護（約 150.663ms 的乾淨 loopback read；連續交易另有 350ms 幀間距）**：是真正的單筆 transaction 延遲主體，但屬於雙 Master／RS485 穩定性防線，維持不動。
3. **CRC 與 sensor 掃描 CPU（本次候選）**：可量測減少 64.96% decode CPU，且在測試範圍內輸出與觀測等價；對目前 15 秒 cadence 的使用者可見延遲影響極小，適合作為批准後的低風險效能清理。

## 建議的下一步（需先批准）

若批准導入，僅將本次候選移植至 `adapters/generic_adapter.py`，保留所有現有日誌字串、封包、CRC 位元組序與驗證流程。部署前應在隔離硬體／實體總線上重跑：正常回覆、碎包、雜訊前後綴、同 UID/FC 舊幀、錯 quantity、讀寫回讀與至少一個完整 4-device 輪替。

若目標是縮短 225 秒資料輪替，需另行批准一份總線負載與外部觀測變更計畫；本報告不主張直接改動 `poll_interval`、`idle_timeout`、`flush` 或 `inter_frame_delay`。
