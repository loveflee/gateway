# 監聽模式鏈路與融斷機制報告

## 結論

監聽模式的程式鏈路完整，且南向採唯讀設計；不過目前 `profile/config.yaml` 只有 `mode: active` 的 UID 1–4，沒有 `mode: listen` 或 `listen_driver`，因此無法以現有設定確認監聽鏈路的實際運作是否順暢。

## 資料鏈路

```text
南向：設備資料 → ListenDriver → ListenMaster → Adapter.feed()
      → 資料檢核／差異快取 → HAManager → MQTT／Home Assistant（北向）

北向命令：Home Assistant → MQTT set topic → 偵測 listen UID → 拒絕寫入
```

`ListenDriver.read_stream()` 每次最多讀取 1024 bytes，讀取等待上限為 5 秒。`ListenMasterDispatcher` 將每個非空 chunk 交給 executor，依序呼叫已註冊 adapter 的 `feed()`；只有回傳非空字典、通過單幀最多 256 keys 與字串長度限制後，才更新該 UID 的 `last_seen`、設備在線狀態與北向資料。

狀態上送會先做差異比對；MQTT state 為 QoS 0、非 retained，最短發布間隔為 200 ms。若遭節流或發布失敗，差異快取會回復，下一有效幀會重試。設備 availability 為 QoS 1、retained。監聽裝置收到 HA 寫入命令時會被明確拒絕，避免干擾側錄總線。

## 離線與融斷門檻

| 機制 | 判定依據 | 門檻與範圍 | 結果 |
|---|---|---|---|
| 單設備離線 | 最後有效、清洗後仍有資料的解碼幀 | `bus.offline_time`；設定缺省時 60 秒；每 UID 獨立 | 該設備 availability 發布 `offline`；下個有效幀立即恢復 `online` |
| 實體斷線 | EOF、socket/serial 例外、重連失敗 | 即時；所有 listen 設備 | 所有設備強制 `offline`，監聽迴圈持續嘗試重連 |
| 解碼融斷 | 整批 adapter 解碼 executor 工作超過 2 秒 | 連續 3 次；整個 ListenMaster 全域 | 強制卸載全部 listen 設備並清除 HA Discovery |

解碼融斷不是以 UID 或 adapter 個別計數，也不是固定秒數的滑動窗口。每一個非空 chunk 的整批解碼最多等待 2 秒；逾時即增加一次。任何一批在 2 秒內結束就歸零，即使沒有解出有效資料。因此連續三批都卡住時，最快約 6 秒觸發；封包間隔較久時，實際時間會更長。

## 融斷後處理

達到第三次逾時後，系統會依序：

1. 將所有監聽設備強制標示為 offline，發布 retained availability。
2. 經 Gateway 安全卸載各 UID：清理 HA manager 快取，並以空 retained Discovery payload 移除 HA 實體，避免殭屍實體。
3. 關閉舊 executor 的尚未開始工作，建立新的四 worker executor，並將逾時計數歸零。
4. 監聽迴圈本身仍繼續，但全部設備已解除註冊；不會自動重新掛載。修正 adapter 或設定後，必須重啟服務才會重新掛載設備。

## 風險與判讀

四個 executor worker 不代表同一 chunk 的四個 adapter 並行：adapter 是在單一工作中依序執行。因此單一 `feed()` 卡死可拖住該批所有設備，並導致全域融斷。已經卡死的 Python worker 無法被強制中止；新 executor 能避免繼續累積新工作，但根因仍須檢查 adapter 的無窮迴圈或永久外部 I/O。
