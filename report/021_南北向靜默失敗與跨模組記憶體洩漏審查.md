
### 完整資料流呼叫鏈追蹤
1. **主動輪詢南向至北向鏈路 (Active Polling)**:
   `driver.read()` $\rightarrow$ `bus_master._process_poll()` $\rightarrow$ `adapter.decode()` $\rightarrow$ `ha_manager.publish_state()` $\rightarrow$ `ha_manager._safe_publish()` $\rightarrow$ `mqtt_client.publish()` $\rightarrow$ `paho.mqtt.client.publish()`.
2. **旁路監聽南向至北向鏈路 (Passive Sniffing)**:
   `listen_driver.read_stream()` $\rightarrow$ `listen_master._listen_loop()` $\rightarrow$ `ThreadPoolExecutor._decode_all_adapters()` $\rightarrow$ `adapter.feed()` $\rightarrow$ `listen_master._process_valid_frame()` $\rightarrow$ `ha_manager.publish_state()` $\rightarrow$ `mqtt_client.publish()`.
3. **北向控制指令至南向鏈路 (Northbound Command)**:
   `MQTT Broker` $\rightarrow$ `main._bridged_on_message()` $\rightarrow$ `main._cmd_queue` $\rightarrow$ `main._mqtt_consumer_task()` $\rightarrow$ `bus_master.submit_write()` $\rightarrow$ `bus_master._process_write()` $\rightarrow$ `adapter.encode_write()` $\rightarrow$ `driver.write()` $\rightarrow$ `adapter.build_verify_read()` $\rightarrow$ `driver.read()` $\rightarrow$ `adapter.decode()`.

## 2. 主題一：南北向資料流的靜默失敗 (Silent Failures)

### 問題 1.1: `bus_master.py` 忽略 `ha_mgr.publish_state()` 回傳值，MQTT 發布失敗仍誤判成功
- **檔案與行號**：
  - `src/bus_master.py` [L367-L368](file:///root/py_ginlong/src/bus_master.py#L367-L368)
  - `src/ha_manager.py` [L114-L116](file:///root/py_ginlong/src/ha_manager.py#L114-L116)、[L206-L220](file:///root/py_ginlong/src/ha_manager.py#L206-L220)
- **模組與函式**：`bus_master.BusMasterScheduler._process_poll` 與 `ha_manager.HAManager.publish_state`
- **分類性質**：**程式碼證據 (Code Evidence)**
- **觸發條件**：MQTT Broker 瞬斷、網路丟包導致 Paho publish 傳回非零 rc、資料含有非 ASCII/非法型別導致 JSON 序列化失敗，或 `_state_cache` 觸發超過 500 keys 拒絕更新時。
- **對外症狀**：設備在實體總線上輪詢成功，但 Home Assistant 上的感測器數值永久停滯不更新；同時 Gateway 內部狀態機將該輪詢視為成功，重置失敗計數器並可能錯誤發布 Online，導致「HA 顯示設備在線但數值凍結」，且後台無任何異常熔斷或離線告警。
- **根因**：`ha_manager.publish_state()` 已在 V3.0.8 改為回傳 `bool`（成功發布回傳 `True`，被節流或發布失敗回傳 `False`）。然而 `bus_master.py` 第 367-368 行未檢查該回傳值，解碼完成後直接無條件呼叫 `self._record_success(uid)`：
  ```python
  # bus_master.py L367-L368
  ha_mgr.publish_state(decoded)
  self._record_success(uid)
  ```
- **信心等級**：**高 (High - 100%)**
- **最小無損修正方案**：
  在 `bus_master.py` 的 `_process_poll` 中檢查 `publish_state` 結果，若北向發布失敗，不應視為完全成功：
  ```python
  # src/bus_master.py L367-L368 修正
  published = ha_mgr.publish_state(decoded)
  if published:
      self._record_success(uid)
  else:
      logger.warning(f"[{uid}] 輪詢解析成功但 HA/MQTT 發布失敗")
      # 可選擇不重置 failure count 或記錄警告
  ```

### 問題 1.2: `bus_master.py` 在 `adapter.build_poll_read()` 失敗時僅重排程，未計入失敗累計
- **檔案與行號**：`src/bus_master.py` [L338-L341](file:///root/py_ginlong/src/bus_master.py#L338-L341)
- **模組與函式**：`bus_master.BusMasterScheduler._process_poll`
- **分類性質**：**程式碼證據 (Code Evidence)**
- **觸發條件**：Adapter 內部狀態損壞、設定檔 read_commands 條目異常或演算法內部拋出未預期例外。
- **對外症狀**：終端日誌持續印出 `adapter build_poll_read 失敗`，但設備在 HA 上的可用性狀態永遠維持原狀（若原為 Online 則永遠維持 Online），系統不會進入 5 次失敗的慢速探測與離線保護（`self._record_failure(uid)` 從未被呼叫）。
- **根因**：`try...except` 捕捉例外後，僅記錄日誌並呼叫 `self._reschedule(uid, scheduled_time)`，跳過了 `_record_failure(uid)`：
  ```python
  # bus_master.py L338-L341
  except Exception:
      logger.exception(f"[{uid}] adapter build_poll_read 失敗")
      self._reschedule(uid, scheduled_time)
      return
  ```
- **信心等級**：**高 (High - 100%)**
- **最小無損修正方案**：
  ```python
  # src/bus_master.py L338-L341 修正
  except Exception:
      logger.exception(f"[{uid}] adapter build_poll_read 失敗")
      if not self._record_failure(uid):
          self._reschedule(uid, scheduled_time)
      return
  ```

### 問題 1.3: `bus_master.py` 寫入驗證值不符耗盡重試時，誤呼叫 `_record_success`
- **檔案與行號**：`src/bus_master.py` [L313-L316](file:///root/py_ginlong/src/bus_master.py#L313-L316)
- **模組與函式**：`bus_master.BusMasterScheduler._process_write`
- **分類性質**：**程式碼證據 (Code Evidence)**
- **觸發條件**：HA 下發寫入指令（如修改充電電流或切換開關），設備實體回覆 ACK 但暫存器實際值未變（例如受限於硬體唯讀、BMS 密碼鎖定或設定值超出設備內部邊界），且所有重試均回讀不符。
- **對外症狀**：寫入操作已徹底失敗，但 Gateway 呼叫 `_record_success(uid)` 重置了該設備的失敗計數器；HA 介面沒有收到寫入錯誤回饋，只能等待下次輪詢覆蓋 UI。
- **根因**：程式碼為了防止「單純回讀值不符導致設備被誤判為 OFFLINE 斷線」，採用 `self._record_success(uid)` 來維持在線，但副作用是同時將 `timeout_count` 歸零並增加 `success_count`，模糊了通訊成功與業務失敗的界線：
  ```python
  # bus_master.py L313-L316
  else:
      logger.error(f"[{uid}] 寫入耗盡，回讀值不符（硬體限制），設備維持 ONLINE")
      self._record_success(uid)
  ```
- **信心等級**：**高 (High - 95%)**
- **最小無損修正方案**：不應呼叫 `_record_success(uid)`（會重置失敗次數），而應僅維持當前狀態或僅記錄 log，不主動干擾狀態機。

### 問題 1.4: `listen_master.py` 解碼異常僅記錄 Log 並丟棄幀，無錯誤累計機制
- **檔案與行號**：`src/listen_master.py` [L230-L232](file:///root/py_ginlong/src/listen_master.py#L230-L232)
- **模組與函式**：`listen_master.ListenMasterDispatcher._decode_all_adapters`
- **分類性質**：**程式碼證據與風險推論 (Code Evidence & Risk Inference)**
- **觸發條件**：旁路總線收到畸變封包、未支援的新韌體資料格式，導致 `adapter.feed()` 拋出 `IndexError` / `ValueError` 等未捕捉例外。
- **對外症狀**：日誌印出 `Adapter 解析崩潰`，該封包被靜默拋棄。若設備持續發送該格式封包，設備在 HA 上數值凍結，直到 60 秒被動看門狗超時才會觸發離線。
- **根因**：多個 Adapter 共享同一串流，單一 Adapter 的解析崩潰被個別 `except Exception` 吞掉以防止影響其他 Adapter，但未對崩潰的 Adapter 累加連續故障計數。
- **信心等級**：**中高 (Medium-High - 85%)**
- **最小無損修正方案**：為每個監聽 Adapter 建立連續解析失敗計數器，連續異常達到門檻時主動標記該設備異常並於 Health Payload 揭露。

## 3. 主題二：跨模組記憶體洩漏與資源持有 (Memory & Resource Leaks)

### 問題 2.1: `mqtt_client.py` 訂閱集合 `_subscriptions` 無 `unsubscribe` 機制
- **檔案與行號**：`src/mqtt_client.py` [L77-L80](file:///root/py_ginlong/src/mqtt_client.py#L77-L80)、[L92-L103](file:///root/py_ginlong/src/mqtt_client.py#L92-L103)；`src/main.py` [L360-L382](file:///root/py_ginlong/src/main.py#L360-L382)
- **模組與函式**：`mqtt_client.RobustMQTTClient.subscribe` 與 `main.EdgeGateway.unregister_device`
- **分類性質**：**程式碼證據 (Code Evidence)**
- **觸發條件**：設備被動態卸載（呼叫 `unregister_device`）或頻繁動態註冊含有不同 Topic 的設備。
- **對外症狀**：長時間運行且發生設備卸載後，`_subscriptions` 集合中的 Topic 永不減少；當 MQTT 斷線重連時，`_on_connect` 會重新訂閱已廢棄設備的所有 Topic，造成 Broker 負載增加與無謂流量。
- **根因**：`RobustMQTTClient` 僅實作了 `subscribe()` 向 Set 增加 `(topic, qos)`，未提供 `unsubscribe()` 清理介面，且 `main.unregister_device()` 亦無退訂邏輯。
- **信心等級**：**高 (High - 100%)**
- **最小無損修正方案**：
  在 `RobustMQTTClient` 中加入 `unsubscribe` 方法並於卸載設備時調用：
  ```python
  # src/mqtt_client.py 新增
  def unsubscribe(self, topic: str):
      with self._sub_lock:
          self._subscriptions = {item for item in self._subscriptions if item[0] != topic}
      try:
          self.client.unsubscribe(topic)
      except Exception:
          logger.exception(f"[MQTT] unsubscribe failed topic={topic}")
  ```

### 問題 2.3: `listen_master.py` 的 `ThreadPoolExecutor` 遇阻塞 Worker 無法強制終止
- **檔案與行號**：`src/listen_master.py` [L109-L111](file:///root/py_ginlong/src/listen_master.py#L109-L111)、[L213-L215](file:///root/py_ginlong/src/listen_master.py#L213-L215)

- **分類性質**：**程式碼證據與已知架構限制 (Code Evidence & Documented Limitation)**
- **觸發條件**：未來新增或修改的 `Adapter.feed()` 內部存在未設置 Timeout 的阻塞式網路/檔案 I/O 或死迴圈。

- **最小無損修正方案**：在規範中嚴格禁止 Adapter 內部進行任何同步阻塞式呼叫，保持純 CPU 記憶體位元組運算。

## 4. 驗證建議與未能證實的限制

### 4.1 驗證建議
1. **MQTT 故障注入驗證**：
   - 暫時關閉本地 MQTT Broker 或在 `ha_manager._safe_publish` 中刻意回傳 `False`，觀察 `bus_master.py` 的 `_record_success` 是否仍被調用，驗證狀態機是否誤判。
2. **記憶體動態增長測試**：
   - 編寫測試腳本對 `mqtt_client.subscribe()` 模擬高頻註冊 10,000 個動態 Topic，檢驗斷線重連時 `_on_connect` 的重送耗時與記憶體佔用。

### 4.2 未能證實的限制
1. **未量化生產環境真實動態卸載頻率**：由於目前設定檔為靜態配置，若生產環境不常呼叫 `unregister_device`，則 `_subscriptions` 集合的洩漏速度極低。
2. **未深入所有非標 Adapter 外部行為**：本次審查以主架構、驅動與官方 Adapter 為主，若未來引入第三方 Adapter 且內部含有未受控的全域快取，仍需個別進行單元審查。
