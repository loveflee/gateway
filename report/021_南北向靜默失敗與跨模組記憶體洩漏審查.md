## 模組關聯圖式文字

## 主題一：南北向資料流靜默失敗 (Silent Failures)

### 1. `ha_manager.py` 發送異常被吞沒，`bus_master.py` 誤判成功
- **檔案與行號**：
  - `src/ha_manager.py` L114-L116 (`_safe_publish` 函式)
  - `src/bus_master.py` L367-L368 (`_arbitration_loop` 迴圈)
- **觸發條件**：MQTT 連線異常、Paho 客戶端拋出例外，或採集到的資料轉換 JSON 序列化失敗時。
- **對外症狀**：設備實際採集到新數值，但在 Home Assistant (HA) 介面上數值卡死不動。系統後台（Gateway）完全沒有斷線告警，反而一直以為發布成功並持續重置錯誤計數。
- **根因**：`ha_manager.py` 的 `_safe_publish` 發生例外時，僅記錄日誌並回傳 `False`。但在 `bus_master.py` 輪詢成功解析資料後，呼叫 `ha_mgr.publish_state(decoded)` 卻沒有檢查該回傳值，隨即呼叫 `self._record_success(uid)`。這導致網關狀態機認為資料已成功上報。
- **信心等級**：高（程式碼明確證據）。
- **最小無損修正方案**：
  ```python
  # 修改 src/bus_master.py L367-L368
  success = ha_mgr.publish_state(decoded)
  if success:
      self._record_success(uid)
  else:
      self._record_failure(uid) # 讓 MQTT 或序列化失敗也計入錯誤閾值
  ```

### 2. `listen_master.py` 解析崩潰靜默丟棄，狀態不同步
- **檔案與行號**：`src/listen_master.py` L230-L231 (`_decode_all_adapters` 函式)
- **觸發條件**：旁路監聽到的封包格式異常（例如受到雜訊干擾），導致 Adapter 解碼拋出 `Exception`。
- **對外症狀**：設備上報了錯誤格式或未知格式的封包，Gateway 無法解析，僅在日誌印出一行錯誤。設備在 HA 仍顯示為 Online，感測器數值永久停滯，未能觸發降級或異常告警。
- **根因**：`except Exception:` 區塊僅有 logging 紀錄，異常封包被捨棄後，Adapter 狀態沒有標記為失敗，也沒有累計連續解析失敗次數的斷線機制（僅依賴實體 `Driver` 的斷線才判定 offline）。
- **信心等級**：中高（風險推論與邏輯證據，設計上過度依賴實體連線狀態）。
- **最小無損修正方案**：
  在 `listen_master.py` 實作類似 `bus_master.py` 的 `_record_failure` 計數與超時機制。當設備連續 N 次或 M 分鐘無法產出有效解碼資料時，將該設備狀態標記為離線並通知 HA。

## 主題二：跨模組記憶體洩漏 (Memory Leaks)

### 1. `mqtt_client.py` 訂閱集合無限制增長 (Memory Leak)
- **檔案與行號**：`src/mqtt_client.py` L78-L79 (`subscribe` 函式)
- **觸發條件**：設備頻繁重新註冊、動態新增/移除、或訂閱主題帶有變動 ID，且無對應的反註冊清理。
- **對外症狀**：長時間運行下，`self._subscriptions` (Set) 持續膨脹，占用記憶體；同時若發生斷線重連，`_on_connect` (L96) 會遍歷該肥大的 Set 重新發起所有（包含已廢棄的）MQTT 訂閱，導致 Broker 負載瞬間飆高及重連嚴重延遲。
- **根因**：`_subscriptions` 集合僅提供 `add` 操作，程式中並未實作 `unsubscribe` 或 `remove` 邏輯。當 `main.py` 呼叫 `unregister_device` 移除設備時，與其相關的指令監聽 topic 永遠殘留在 Set 中。
- **信心等級**：高（程式碼明確證據）。
- **最小無損修正方案**：
  於 `mqtt_client.py` 擴充 `unsubscribe` 介面，並在設備卸載時呼叫：
  ```python
  def unsubscribe(self, topic: str):
      with self._sub_lock:
          self._subscriptions = { (t, q) for t, q in self._subscriptions if t != topic }
      try:
          self.client.unsubscribe(topic)
      except Exception:
          logger.exception(f"[MQTT] unsubscribe error topic={topic}")
  ```

### 2. 背景任務與執行緒資源懸空風險 (Thread Leak)
- **檔案與行號**：`src/listen_master.py` L213-L215 (`stop` 函式)
- **觸發條件**：Adapter 的 `feed()` 實作不良，內部意外發起了同步阻塞的 I/O 請求（如 `requests.get`、無窮迴圈）。
- **對外症狀**：Gateway 執行關機或熱重啟指令時，進程卡死。即使主程式強制發送了 `shutdown(wait=False, cancel_futures=True)`，底層卡在 I/O 的 Thread 並不會被釋放，若以守護進程模式執行將導致殭屍執行緒洩漏。
- **根因**：Python 的 `ThreadPoolExecutor` 若設為 `wait=False` 只是不再接收新任務，並無法強制中斷正在執行的阻塞執行緒（OS level thread）。原作者在 L210 註解中亦坦承此風險。
- **信心等級**：中（風險推論，取決於未來的 adapter 實作品質）。
- **最小無損修正方案**：嚴格審查所有 `adapters/` 模組的 `feed()`/`decode()` 實作，禁止任何 Blocking 呼叫；或為 Worker 加上超時強制自盡的看門狗邏輯。

## 驗證建議與未能證實的限制

1. **驗證建議**：
   - **靜默失敗驗證**：暫時於 `adapter` 解碼階段植入 `raise ValueError("Test")`，觀察 HA 的數值是否停滯，確認後台是否無法感知設備「軟性」斷線。
   - **記憶體洩漏驗證**：在測試環境寫一個迴圈連續呼叫 10,000 次 `mqtt_client.subscribe("test/dynamic/topic/X")`，觀察 `_subscriptions` 佔用的 Heap 大小，並觸發斷線重連，監測 MQTT 網路突波。
2. **未能證實的限制**：
   - 由於目前採唯讀審查，未逐一檢視 `adapters/` 目錄下所有廠商插件（如 `st_inverter_adapter.py`, `jkbms_adapter.py`）的具體實作，無法證實目前是否已存在具體的無窮迴圈或阻塞點。
   - 缺乏執行期的 Heap 記憶體剖析 (如 `tracemalloc`) 抓取 Dump，無法確切量化 `_subscriptions` 在現行部署下每日膨脹的真實位元組數。
