# 013 熔斷復原方案獨立驗證

## 執行裁決

**不背書 012 的「鎖定 + uptime 退出 + 初始 availability」為完整方案。**其中「保留 HA manager／Discovery、熔斷後不再提交 decode」可行且必要；但全程序 `os._exit(75)` 會影響 active 軌，且 012 的初始 availability 修正未處理現行 MQTT callback 的發布順序，仍存在 HA 將舊 state 短暫顯示為可用的窗口。012 的沙箱原型亦未把 guard 接入真正的 `_listen_loop()`。

最小、非破壞性且對本熔斷路徑一致的方案是：**每次熔斷都鎖定監聽解碼、不退出程序**；保留 manager／Discovery／state cache，對監聽設備發布 retained `offline`，在 `run_in_executor()` 前跳過後續工作。再補兩個一致性措施：註冊時快取 `offline`，且 MQTT reconnect 時先補發已有 cache 的設備 availability、再發布 gateway `online`。若需自動回收真卡死，應將 listen 軌拆為獨立服務／process；這不是最小修正。

## 決策表

| 方案 | 可行性 | 對外行為 | 裁決 |
|---|---|---|---|
| 012 鎖定 fallback | 可行 | 實體保留、offline、停止新工作；但 health 未標示熔斷原因 | 採其核心 |
| 012 uptime 後 `os._exit` | 可行但不完整 | 重啟整個 gateway；active 軌也受 LWT／舊 retained status 影響 | 不採用 |
| 012 初始 `offline` 一行 | 必要但不足 | callback 先發 gateway online，後續才補設備狀態，仍有窗口 | 與順序修正合併採用 |
| 熔斷即鎖定 + callback 順序修正 | 可行、最小 | 保留 Discovery/state，設備 unavailable，active 軌不停 | **建議** |
| 每 adapter 長駐子行程 | 可行但大型改造 | 可真隔離／重啟單一 adapter；需 IPC、state/buffer、背壓設計 | 僅在需自動復原時採用 |

## 主要證據與缺口

現況熔斷會呼叫 `unregister_device()`、清 Discovery、重建 executor（`src/listen_master.py:216-244`）；一次 decode job 仍依序跑所有 adapter（`:162-182`）。012 正確指出移除該清理並在提交前 guard 的必要性。

但 012 的 `PatchedDispatcher` 只新增獨立 `submit_decode()`，沒有覆寫或修補真正的 `_listen_loop()`；production 實際提交點仍是 `run_in_executor()`（`scratch/validation_012/harness2_recovery.py:54-85`；`src/listen_master.py:197-245`）。其 R1/R3 直接呼叫 `on_fuse_blown()` 後才測 guard，未經由三次 timeout 觸發（`harness2_recovery.py:104-128,171-204`），故不能證明整合後確實停止提交。

初始 `set_availability(False)` 會將 cache 設為 false，即使當時 broker 未連線（`src/ha_manager.py:222-240`），但現行 reconnect callback 先發 gateway `online`（`src/main.py:398-400`），只在切回 event loop 後才分批 `republish_availability()`（`:405-435`）。若 broker 留有裝置 `online`，gateway-first 窗口中雙 availability 都是 online；HA 使用 `availability_mode: all`（`src/ha_manager.py:265-269`），會顯示舊 state 為可用。012 的 boot harness 在註冊前就發 Discovery，且 Mock 已連線（`harness2_recovery.py:87-96`），未覆蓋此啟動順序。

更嚴重的是 active 與 listen 可同時存在，只禁止共用同一通訊埠（`src/main.py:637-645`）。listen 融斷的 `os._exit` 會令整個 gateway LWT offline；重啟後 gateway online 先發布，舊 active device retained `online` 仍可讓 active 實體在下一輪 poll 前顯示可用。這是把單一 listen adapter 故障擴大成 active 軌可觀測性回歸。`os._exit` 也會略過 `stop()` 的 MQTT flush／driver 關閉（`src/main.py:1009-1092`）。

鎖定方案的殘餘限制是最多三個已開始的 worker 無法回收，人工優雅重啟仍可能等 Docker 強制結束（`src/listen_master.py:139-160`）。health 目前只輸出 listen `online`、固定 timeout/success 與 mode，沒有 `decoding_disabled` 或 fuse 原因（`src/main.py:546-563`）；應新增布林／原因欄位並把既有「強制卸載」CRITICAL 改成「已鎖定、需重啟」，否則 MQTT health 與 log 語意不完整。state 應保留最後值但保持 unavailable；鎖定後不可發布新 decode state。

## 獨立驗證

只在 `scratch/validation_013/` 新增離線 harness；直接載入現行 `src/ha_manager.py` 與 `src/listen_master.py`，使用 MockBroker 和延遲 adapter，未連線 MQTT／硬體。

```bash
cd /root/py_ginlong
python3 -u scratch/validation_013/harness.py
```

結果：**6/6 PASS**（`scratch/validation_013/results.json`）。T1 驗證三次 timeout 後鎖定仍保留 2 個 Discovery、發布 offline 且後續 8 個 chunk 零提交；T2 驗證 broker retained 遺失後可補回 Discovery/offline；T3 以離線 publish 模擬證實 gateway-first stale-online 窗口；T4 證實 listen `os._exit` 可令 retained active device 在重啟、重輪詢前顯示 online；T5/T6 靜態確認 callback 順序與 health 缺欄位。harness 的實作與結果見 `scratch/validation_013/harness.py:64-205`。

## 邊界

未修改 `src/`、`adapters/`、`profile/`、Docker／compose 或容器；未啟停容器、未連線硬體或實體 MQTT。現行設定沒有 listen 裝置，故本結論為靜態與 Mock 語意驗證，尚需在獨立 listen 環境進行整合驗收。
