# 024 — 6k2 合併讀取實機 10 分鐘觀察報告

日期：2026-08-10  
觀察對象：S6-EH1P6K，`192.168.106.14:502`，刻意雙 master 壓力環境。  
觀察結論：**`6k2` 已正確載入、四組合併請求已實際送出且 TCP 重組後 CRC 正確；但本觀察窗沒有取得任何可驗證的合併讀取 RX 回應、資料解碼或 HA state 上報。因此硬體相容性驗收為「未通過／無法判定」，不是已證實成功，也不能在沒有相同基準觀察的情況下歸因為 `6k2` 缺失。**

依任務前提，雙 master 為刻意的地獄式穩定性測試，不列為系統缺失。本報告如實記錄它對驗收訊號的影響。

1. 容器內 `map_validator.py /app/profile/6k2.yaml`：**通過**。

3. 這些驗證不送出 Modbus 請求；重啟後的實機請求才是本報告後段的觀察資料。

## 10 分鐘實機觀察

### 容器與 HA

- `ginlong` 在觀察末仍為 `running`。
- 重啟後 HA Discovery：UID 1–4 **4/4 均完成**。
- 容器內以既有 MQTT 憑證建立 15 秒唯讀訂閱：連線 `RC=0`，但 `py_ginlong/+/+/state` 收到 **0** 則 state message。
- 日誌中沒有 `publish rc=` 或 MQTT 發布失敗紀錄。這表示 MQTT broker 可連線、Discovery 可送出；但本視窗沒有成功解碼的資料可發布成 state。

### TX/RX：以 TCP sequence 重組後解碼

被動擷取使用 `ens18`、`host 192.168.106.14 and tcp port 502`，不送出任何封包。擷取檔：[6k2_10m_modbus_retry.pcap](/root/Documents/Codex/2026-08-09/root-ginlong-master-1-2-report/test/continuous_read/observations/6k2_10m_modbus_retry.pcap)。

- 時段：`19:54:43.617`–`20:04:34.379 +08:00`（約 9 分 51 秒）。
- 封包：47,243；核心丟包：**0**；檔案大小：3,449,806 bytes。
- 唯一有 payload 的 TCP 連線：`192.168.106.68:52050 ↔ 192.168.106.14:502`。
- 與 Modbus server 方向的 TCP sequence 重組：gap **0**、略過重傳重複 bytes **0**。故下列 TX 結果不是單一 TCP segment 誤判。

| 重組且 CRC 正確的 TX RTU request | 次數 |
|---|---:|
| `read_pv_and_dc_power`（FC4, 33049, count 10） | 7 |
| `read_grid_and_status`（FC4, 33073, count 24） | 6 |
| `read_meter_battery_all`（FC4, 33133, count 18） | 5 |
| `read_energy2_all`（FC4, 33161, count 20） | 7 |

反向 RX 共含 23,579 個 TCP payload packet、118,469 payload bytes，同樣沒有 TCP sequence gap；但重組後找不到任何一個 CRC 正確、byte-count 符合目標的 FC3／FC4 正常 RTU response。這與 application log 的 CRC 防護拒絕及 MQTT state 0 則互相一致。

舊的 [l4.py](/root/test/l4.py) 會逐一 TCP segment 計算 RTU CRC，不能處理這類分段；本次改用 [analyze_rtu_tcp_pcap.py](</root/Documents/Codex/2026-08-09/root-ginlong-master-1-2-report/test/continuous_read/analyze_rtu_tcp_pcap.py) 依 TCP sequence 重組。完整輸出在 [6k2_10m_rtu_tcp_summary.json](</root/Documents/Codex/2026-08-09/root-ginlong-master-1-2-report/test/continuous_read/observations/6k2_10m_rtu_tcp_summary.json)。

## 判定

| 驗收面向 | 判定 | 證據 |
|---|---|---|
| YAML／Map 結構 | 通過 | 容器 map validator 通過。|
| Sensor 位址與資料長度等價 | 通過 | 49 個啟用 sensor 與原圖完全相同。|
| 合併 TX 組包與實際套用 | 通過 | 25 個目標合併 request 均經 TCP 重組及 CRC 驗證。|
| RX 回應／資料解碼 | 無法通過 | 10 分鐘沒有可驗證的目標正常 response。|
| HA Discovery | 通過 | 4/4 完成。|
| HA state 上報 | 無法通過 | MQTT 訂閱 0 則，且沒有成功解碼資料。|
| `6k2` 導致通訊問題 | 無法判定 | 雙 master 壓力中沒有舊圖同窗基準，不能歸因。|

## 後續選項

目前 `6k2` 仍為四個 UID 的 active profile，未自動回復，因任務授權了長時間觀察。若要完成「硬體相容性」驗收，需要在相同設定下取得至少一個可驗證的正常 response／HA state，或取得同時段舊圖基準後才可比較。若不再延長觀察，應由操作者明確決定是否把四個 UID 回復為 `solis_inverter_map`；本報告不自行改變這個已授權的測試狀態。
