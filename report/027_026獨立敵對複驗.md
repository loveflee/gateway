## 5. Codex 的缺漏（必須修正的一項）

### ⚠️ P1-2「verify 驗 exact byte count」未評估雙 master 行為變更

Codex P1-2 原文：「由 `decode()` 驗 exact byte count」—— **未區分新的多暫存器路徑與既有 count=1 路徑**。

**現況實測**（`dualmaster.py`）：

```
verify request (verify_count 未設 → 1 register) = 01 03 00 64 00 01 C5 D5
   依規格回應應為 7 bytes（byte_count=2）

  正確 1 register   ( 7B) ✅ 接受 → {'k': 4660}
  外來 2 registers  ( 9B) ✅ 接受 → {'k': 4660}
  外來 6 registers  (17B) ✅ 接受 → {'k': 1}
```

`decode()` 的 verify 分支只呼叫 `_verify_modbus_frame(raw_data, expected_fc=read_fc)`，**不帶 `expected_data_bytes`** → 任何長度的同 UID/FC 合法幀都被接受，且只取前 2 bytes。

**後果鏈**：

| | 現況 | 若對 legacy count=1 也加 exact byte count |
|---|---|---|
| 雙 master 外來幀 | 被接受 → 回讀值與寫入值不符 → **值不符** | `DataDecodeError` → `physical_fault_count += 1` |
| bus_master 帳務 | `_record_success`，**設備維持 ONLINE** | 重試耗盡 → `_record_failure` → 連續 5 次可推向 **OFFLINE** |

依使用者的前提：雙 master 造成的碰撞不列為缺失，**但若升級使雙 master 環境下原有行為退化則必須列為回歸**。此項符合後者 —— 不是防護能力退化，而是**既有設備在噪音下的 online/offline 判定會改變**。

**修正**：exact byte-count 檢查**只套用於新的多暫存器路徑**（`verify_count > 1` 或 codec 判定為多字）。`verify_count` 未設或為 1 的既有路徑，**decode 行為必須逐位元組維持現狀**，並以 snapshot test 證明。

### 次要缺漏（不影響裁決）

1. **`link_sensor` 分支在正式 profile 從未被使用。** 五個 setting 的 `link_sensor` 全為 `None`，實際只走同名 fallback。Codex 描述為「優先 `link_sensor`，沒有才用同名」，語意正確但會讓人誤以為兩條路徑都經現場驗證。**測試設計必須明確涵蓋 `link_sensor` 分支**，它是未經現場執行的新程式路徑。
2. **基準宣告未涵蓋設定與候選 profile**（見 §1）。

## 8. 裁決

# PASS WITH CHANGES

Codex 的事實查證、PyModbus 引用、隔離驗證與升級方向**全部成立**，本輪未發現任何造假、誤引或推論跳躍。但下列一項必須修正後才可實作：

### Codex 哪項錯

**P1-2「由 decode() 驗 exact byte count」未區分新舊路徑**，會改變既有 5 個 Solis setting 在雙 master 噪音下的 online/offline 判定（實測：外來長度的合法幀目前被接受並落入「值不符」，收緊後改判物理故障）。

### 正確應該怎麼改

exact byte-count 檢查**僅套用於新的多暫存器 verify 路徑**；`verify_count` 未設或 = 1 的既有路徑，`decode()` 行為必須逐位元組維持現狀，並以 snapshot regression test 鎖定。

### 修正後真正的最小方案

| 優先 | 內容 | 檔案 |
|---|---|---|
| **P0-1** | 拒絕溢位與非有限數值（`> 0xFFFF`、`NaN`、`Inf` 統一 `ValueError`），不得靜默遮罩 | `adapters/generic_adapter.py` `encode_write()` |
| **P0-2** | 文件／註解標明現況為「FC16 count=1 only」 | 註解／capability matrix |
| **P1-1** | FC16 quantity=2 的 `uint32`／`int32`／`float32` encoder，codec 由 `link_sensor` → 同名 sensor 推導；無來源時**保留既有單一 `uint16` 行為** | `encode_write()` + 私有 helper |
| **P1-2′** | 多暫存器 verify codec，**exact byte count 僅套用於多字路徑**；legacy count=1 逐位元組不變 | `build_verify_read()` 的 context + `_extract_data()` |
| **選配** | validator 收緊（read FC 白名單與數量上限、write FC 白名單、`verify_count >= 1`、已知 datatype／word_order）—— 與 P0/P1 **獨立**，可延後 | `src/map_validator.py` |

**不做**：FC15、FC22、FC23、64-bit、新增 profile 欄位、改 Driver／BusMaster／MQTT／HA／Docker、PyModbus 納入 production dependency。

**驗收必須包含**：
1. FC05／FC06／現有 FC16 count=1 的 byte snapshot 完全相同
2. `verify_count` 未設或 = 1 的 verify decode **對外來長度幀的處置與現況逐位元組相同**（防雙 master 回歸）
3. `link_sensor` 分支的顯式測試（現行 profile 未涵蓋此路徑）
4. `70000`／`-70000`／`NaN`／`Inf` 統一 `ValueError`，且不影響 online/offline
