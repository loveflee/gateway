# 0091_claude 可行性與最小無損方案

## 範圍與執行建議

本報告只評估 `report/0091_claude.md` 的監聽融斷與啟動重連提案；未修改程式或設定。**建議採用「任何熔斷即解碼鎖定停用」：保留 adapter、HA manager、Discovery 與 state cache，只發設備 `offline`，停止提交新的 `feed()` 工作，等待人工重啟。**另將「listen 初始連線失敗仍啟動並交給既有退避重連」列為獨立、可採用的可用性修正。

這比 0091 的 uptime 分流更小且決定性：沒有任意的五分鐘界線、沒有 `os._exit()`，同時把永久卡住的工作數上界維持在觸發門檻的三個。它不是讓卡住的解碼自動恢復；Python thread 無法安全中止，正確的恢復動作仍是受控重啟。

## 決策表

| 方案 | 可行性 | 對 MQTT／HA 一致性 | 結論 |
|---|---|---|---|
| 熔斷後直接 `os._exit(75)` | 技術上可行 | Discovery 可保留，但 0.3 秒不保證 QoS 1 的設備 offline 已送達；重啟後舊 retained `online` 可能配合 gateway `online` 使陳舊 state 暫顯可用 | 不建議 |
| 0091 uptime >5 分鐘退出、否則 `_decoding_disabled` | 可行，但判定不穩定 | fallback 路徑可保留實體；退出路徑仍有上述 retained 狀態競態 | 不建議作為最小方案 |
| 熔斷即鎖定停用（建議） | 可行，約需旗標、提交前 guard、熔斷分支各一處 | 保留 Discovery／state；設備 QoS 1 retained `offline`，MQTT 重連可由既有 cache 補發 | **建議** |
| 初始 listen 連不上仍啟動 | 可行，無須新增重連狀態機 | 裝置先 unavailable，連線後有效幀才 online；不影響 active 軌 | 建議獨立實測後採用 |
| 熔斷時重建 adapter／清 buffer | 不安全 | 舊 worker 仍持有同一 adapter；跨 thread 重設 buffer 會競態並可能丟幀 | 不採用 |
| JKBMS `MAX_ITER`／子行程隔離 | 前者可做、後者可做但大幅重構 | `MAX_ITER` 清 buffer 會丟不完整資料；子行程需處理 stateful buffer、IPC、child 生命週期 | 非最小，暫不採用 |

## 證據與評估

目前第三次 2 秒逾時後，程式先將全部設備 offline，接著經 Gateway `unregister_device()` 清除 Discovery、刪除 adapter/HA/cache，並重建 executor；因此 HA 實體會被移除而非僅 unavailable（`src/listen_master.py:216-244`；`src/main.py:348-369`；`src/ha_manager.py:118-176`）。一次 executor 工作依序處理所有 adapter，一台阻塞即拖住整批（`src/listen_master.py:162-182`）。

0091 的直接退出方案可由 compose 的 `restart: unless-stopped` 重啟（`docker-compose.yaml:3-6`），且非緩衝日誌已啟用（`Dockerfile:4-6`）。但 `os._exit()` 會略過 `stop()` 的 MQTT flush、driver 關閉與正常關機處理（`src/main.py:1009-1092`）。`_force_all_offline()` 的 publish 僅排入 Paho，程式沒有等待每個 publish 完成（`src/listen_master.py:184-195`；`src/mqtt_client.py:69-75`）；0091 的 0.3 秒因此不是送達保證。新進程的 HA manager 初始 availability cache 為 `None`（`src/ha_manager.py:53-60`），重連只補「已有 cache」的 availability（`src/ha_manager.py:77-89`），故遺留的裝置 retained `online` 有機會與新發的 gateway `online` 同時成立。HA 使用兩個 availability topic 的 `all` 模式（`src/ha_manager.py:265-269`），這會短暫把陳舊 state 呈現為可用。

0091 的 uptime 守衛本身無法辨認「冷啟動即持續故障」與「剛重啟後持續故障」：`start_time` 在每個新 `EdgeGateway` 都重設（`src/main.py:163-167`）。五分鐘閾值也未由目前配置或測試佐證。其 fallback 的核心 `_decoding_disabled` 是正確方向，但不需要先退出一次；直接鎖定可避開重啟迴圈與上述 retained 競態。現行閾值為連續三次，故鎖定前最多已有三個逾時工作；guard 必須放在 `run_in_executor()` 之前，否則仍會持續耗盡 worker（`src/listen_master.py:204-245`）。

建議實作語意為：熔斷時呼叫既有 `_force_all_offline()`，設置 dispatcher 私有的 `decoding_disabled`，記錄一條明確 CRITICAL（含「已鎖定、需重啟」），而**不**呼叫 `unregister_device()`、不清 Discovery、不重建 executor。後續 chunk 仍可由 driver 讀取／側錄，但略過 decoder 提交。如此 `device_states` 仍保留且 health 會呈現 listen UID offline（`src/main.py:546-563`）；若當下 MQTT 不可用，保留下來的 HA manager 在 MQTT 回連時會重新送 Discovery 與 cache 中的 offline availability（`src/main.py:420-439`；`src/ha_manager.py:77-89`）。最後一次有效 state 保留但整體 unavailable，符合 HA 的可觀測語意。這是「不額外破壞資料」：永久卡住的 `feed()` 本來就無法解析的後續幀不可能被任何 thread 方案無損救回。

初始連線修正亦可行。現行 `main.py` 在第一次 `listen_driver.connect()` 為 false 時退出（`src/main.py:695-731`）；但 driver 已有 runtime 退避重連：TCP 1 秒起、上限 5 秒（`src/listen_driver.py:117-161`），USB 上限 10 秒（`src/listen_driver.py:225-270`）。僅對「設定已驗證、driver 已建立、實體 connect 回傳 false」改為繼續建立 dispatcher，即可讓 `read_stream()` 觸發既有重連；不得放寬缺少欄位或不支援 type 的 fatal 驗證。首次失敗時應立即或首次重連失敗後發布設備 offline，否則 HA 在第一個退避週期沒有明確設備狀態。

## 風險、替代方案與驗證

鎖定停用的代價是需人工重啟，且三個已卡住的 non-daemon worker 仍可能使優雅停止等待 Docker 強制結束；這是已知 Python 限制（`src/listen_master.py:139-160`）。同時應避免把「2 秒」直接等同 adapter bug：JKBMS 現行 `feed()` 的所有迴圈分支會刪 buffer 或 `break`，且無 I/O、sleep、lock（`adapters/jkbms_adapter.py:311-430`）；但 CPU 飢餓、未來 adapter 或超大直接輸入仍可能逾時。現行 `profile/config.yaml` 沒有 listen 裝置，不能在此環境宣稱實機驗證（`profile/config.yaml:22-46`）。

若需求改為「自動隔離壞 adapter 並自動恢復其餘設備」，較佳但非最小的替代方案是每個 adapter 長駐獨立 process，讓其 buffer/state 留在 child，主程序以有界 IPC 收結果，逾時只終止該 child。它可真正回收卡死程式碼並隔離 UID，但必須處理 IPC 背壓、child 重建、幀遺失與 state 同步；不宜以目前 executor 熔斷的小修取代。

驗證：已靜態追蹤 0091、listen driver/master、Gateway、HA/MQTT、JKBMS adapter、compose 與現行設定；未修改檔案、未重啟容器、未連接實體設備。後續至少需以假 adapter 注入永久阻塞與延遲返回兩案，驗證 HA Discovery 未被清除、device availability retained 為 offline、MQTT 回連補發、active 軌不中斷，以及初始 TCP/USB 不可用後的退避與恢復。
