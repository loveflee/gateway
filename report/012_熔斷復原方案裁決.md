## 1. 執行裁決（Executive Verdict）

**兩案皆不完整,但缺口互補;合併後即為完整方案。**

- **011 找到的 retained `online` 競態屬實**,已於沙箱實證（T2/T3）。它足以否決 0091 **原樣**的退出方案 —— 該競態會讓 HA 把陳舊數值顯示為「可用」。
- **但 011 據此否決整條退出路線,判斷過當**。競態成因是「新進程從不發布設備初始 availability」（`listen_master.py:86-104` 全程不呼叫 `set_availability`）,與退出機制正交;補一行即關閉（T4 實證）。011 自己在啟動修正段亦建議同一件事。
- **011 對 uptime 守衛的兩點批評:一條成立、一條不成立**。「retained 競態」成立;「`start_time` 每進程重設故無法區分冷啟動與重啟後故障」技術描述正確（`main.py:166`）,但該區分不影響決策 —— 兩者皆應鎖定（T6 實證四情境全部導向正確結果）。
- **0091 未評估的重啟迴圈風險成立**：啟動約 5s + 熔斷約 6s ≈ 11s > Docker 重置退避門檻 10s → 退避永遠累積不起來 → 緊迫重啟迴圈,WebUI 救援路徑失效（T7）。
- **採 011 的鎖定機制作為 fallback、保留退出路徑處理暫時性卡頓、並補上初始 availability**,三者合併後嚴格優於任一單案（R1–R4 實證）。

### 對委派問題的直接回答：修正後監聽能否正確恢復上報？

| 故障類型 | 是否恢復上報 | 依據 |
|---|---|---|
| **暫時性卡頓**（CPU 飢餓、容器節流、單次極慢但終會返回） | ✅ **自動恢復,無需人工介入** | R2：重啟後 availability 由 `offline` → `online`,state 正常上報,全程未刪除 HA 實體 |
| **真卡死**（無窮迴圈／鎖／外部 I/O 永久阻塞） | ⚠️ **不會自動恢復,但停在可診斷狀態;adapter 修好並重啟後完整恢復** | R3：一次重啟後收斂為鎖定,不進入無限迴圈;修好後 availability 回 `online` |
| **HA 實體本身** | ✅ **任何路徑都不再被刪除** | R1/R2/R3：Discovery retained 全程保留,最差僅 `unavailable` |

**真卡死無法自動恢復是 Python 的硬限制**（無法中止執行中的 thread）,任何熔斷機制皆然;現況、0091、011、本建議案在這點上完全相同。差別只在「刪不刪實體」與「要不要試一次重啟」。

## 3. 缺陷證據與程式碼定位

### 3.1 現況：熔斷會刪除 HA 實體（非僅 unavailable）

| 環節 | 位置 |
|---|---|
| 熔斷分支呼叫 `app_state.gateway.unregister_device(uid)` | `src/listen_master.py:236` |
| fallback 呼叫 `self.unregister_device(uid)` | `src/listen_master.py:238`、`:240` |
| Gateway 端隨即 `send_discovery(cleanup=True)`（發空 retained = 刪實體） | `src/main.py:356` |

**T1 實證**：熔斷後對 Discovery topic 發出 6 則空 retained,broker 上殘存的 Discovery retained 歸零。

### 3.2 011 的核心發現：retained `online` 競態

| 環節 | 位置 |
|---|---|
| `_availability_cache` 初值為 `None` | `src/ha_manager.py:54` |
| `republish_availability()` 在 cache 為 `None` 時提早 return | `src/ha_manager.py:85` |
| `register_device()` 全程不呼叫 `set_availability` | `src/listen_master.py:86-104` |
| `_check_offline_status` 兩個分支皆要求 `state["online"] is True` | `src/listen_master.py:321` 起 |
| HA 採 `availability_mode: all`（雙 topic 皆須 online 才可用） | `src/ha_manager.py:269`、`:305` |
| 僅 `stop()` 的 LWT 有 `wait_for_publish`;`_force_all_offline` 沒有 | `src/main.py:1069` vs `src/listen_master.py:184` |

**T2/T3 實證**：新進程 `_availability_cache = None` → `republish_availability()` 未覆蓋 broker 上的陳舊 `online`;而卡死設備永遠收不到有效幀,故 `_check_offline_status` 兩分支永不成立 → 陳舊 `online` 永久存活 → 與新進程的 gateway `online` 同時成立 → HA 顯示陳舊 state 為「可用」。

## 4. 建議方案（最小無損）

> 以下為**建議**,本輪未實作。

### 4.1 `listen_master.py` — 註冊時發布初始 availability（約 2 行,獨立價值）

`register_device()` 回傳 `True` 前呼叫一次 `ha_manager.set_availability(False)`。

關閉 §3.2 競態,並讓「尚未收到任何有效幀」在 HA 上有明確語意。**不論最終採哪案都應納入**;亦使 MQTT 重連補發生效（`_availability_cache` 不再為 `None`,見 R4）。

### 4.2 `listen_master.py` — 熔斷分支改造

**移除**：`app_state.gateway.unregister_device()`、`self.unregister_device()`、`send_discovery(cleanup=True)` 整條路徑、executor 重建。

**改為**：

```
_force_all_offline()                    # 既有函式，保留實體僅設 unavailable
if process_uptime > 300s:               # 暫時性 → 值得試一次重啟
    CRITICAL(「解碼熔斷，保留 Discovery，交由 Docker 重啟」)
    await asyncio.sleep(0.3)
    os._exit(75)
else:                                   # 重啟後又立刻熔斷 = 持續性故障
    _decoding_disabled = True
    CRITICAL(「持續性故障，已鎖定解碼；實體與 WebUI 保留供診斷，請排查 adapter.feed()」)
```

**不得走 `gateway.stop()`**：它會對每台呼叫 `unregister_device()` → 清 Discovery（`src/main.py:1057` → `:356`）,正是要避開的路徑。

### 4.3 `listen_master.py` — 提交前 guard

`_decoding_disabled` 為真時,收到 chunk 直接跳過 `run_in_executor()`。

**必須置於 `run_in_executor()`（`src/listen_master.py:211`）之前** —— T5 實證：只要仍提交,4 個 worker 會被燒光,guard 置於取回結果之後無效。driver 讀取與 `app_state.traffic_log` 側錄不受影響。

### 4.4 待裁決：listen 首次連線失敗不 `sys.exit`

009 與 011 皆建議。技術上可行且無須新增狀態機 —— `listen_driver` 已有完整退避重連（TCP 1s 起上限 5s、USB 上限 10s,含 jitter）。

**但此項與先前施工令的既有裁決（「先啟動＋退避重連狀態機整組退貨」）衝突,需決策者明示是否推翻。** 若採用,範圍應嚴格限於「設定已驗證、driver 已建立、實體 `connect()` 回傳 false」,**不得**放寬缺欄位或不支援 type 的 fatal 驗證。

## 6. 殘餘風險

1. **已卡死的 worker 無法回收**（最多 3 個,為熔斷門檻）。它們是 non-daemon thread,直譯器退出前會 `join`,故優雅關機仍可能等到 Docker grace period 用完被 SIGKILL。此為 Python 硬限制,`listen_master.py` V1.13 的關機診斷即為此而設。**任何非子行程方案皆無法消除。**

2. **300 秒門檻為可調參數**。011 指其「未由配置或測試佐證」屬實。選值理由：須遠大於「啟動 + 熔斷」單次週期（約 11s,T7）,以確保「重啟後又立刻熔斷」必然落入鎖定路徑。建議實作時設為具名常數並於註解說明,而非硬編字面值。

3. **`os._exit(75)` 會略過 `stop()`**：不執行 MQTT flush 與 driver 關閉。USB FD 由 OS 於進程結束時回收;MQTT LWT 會觸發 gateway `offline`,使實體於重啟窗口內顯示 unavailable —— 此為預期且正確的行為。

4. **MQTT 於熔斷當下不可用時**：`_force_all_offline()` 與重啟後的初始 `set_availability(False)` 皆會發布失敗,但 `_availability_cache` 已為 `False`,MQTT 重連時 `republish_availability()` 會補回 `offline`（R4 實證）。**前提是 HAManager 未被銷毀** —— 這正是不可再呼叫 `unregister_device()` 的另一個理由。

5. **沙箱驗證的固有限制**：本輪以逐字複製件 + Mock 驗證行為語意,**未在整合執行期實測**。

6. **本專案現行環境無法實機驗收**：`profile/config.yaml` 中 `mode: listen` 設備數為 **0**,`ListenMaster` 根本不會被建立。**真正的實機驗收必須在 py_jkbms 進行**,而該環境目前未執行且程式碼版本較舊。建議順序：先讓 py_jkbms 跑上目前版本並確認基準線 → 再實作本方案 → 於該環境完成注入驗證。
