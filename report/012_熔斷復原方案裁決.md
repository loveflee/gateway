### 對核心問題的回答：修正後監聽能否恢復上報？

| 故障類型 | 是否恢復 | 依據 |
|---|---|---|
| **暫時性卡頓**（CPU 飢餓、容器節流、單次極慢但終會返回） | ✅ **自動恢復,無需人工介入** | 重啟後 availability `offline` → `online`,state 正常上報,全程未刪除 HA 實體 |
| **真卡死**（無窮迴圈／鎖／外部 I/O 永久阻塞） | ⚠️ **不會自動恢復,但停在可診斷狀態;adapter 修好並重啟後完整恢復** | 一次重啟後收斂為鎖定,不進入無限迴圈 |
| **HA 實體本身** | ✅ **任何路徑都不再被刪除** | Discovery retained 全程保留,最差僅 `unavailable` |

真卡死無法自動恢復是 **Python 的硬限制**（無法中止執行中的 thread）,現況與三個提案在這點上完全相同;差別只在「刪不刪實體」與「要不要試一次重啟」。

### 3.1 熔斷分支移除 `unregister_device()` 與 Discovery cleanup

| 環節 | 位置 |
|---|---|
| 熔斷呼叫 `app_state.gateway.unregister_device(uid)` | `src/listen_master.py:236` |
| fallback 呼叫 `self.unregister_device(uid)` | `src/listen_master.py:238`、`:240` |

### 3.2 `register_device()` 補 `set_availability(False)`（關閉 retained 競態）

| 環節 | 位置 |
|---|---|
| `_availability_cache` 初值為 `None` | `src/ha_manager.py:54` |
| `republish_availability()` 在 cache 為 `None` 時提早 return | `src/ha_manager.py:85` |
| `register_device()` 全程不呼叫 `set_availability` | `src/listen_master.py:86` |
| `_check_offline_status` 兩分支皆要求 `state["online"] is True` | `src/listen_master.py` 尾段 |
| HA 採 `availability_mode: all` | `src/ha_manager.py:269`、`:305` |
| 僅 `stop()` 的 LWT 有 `wait_for_publish`,`_force_all_offline` 沒有 | `src/main.py` vs `src/listen_master.py:184` |

**機制**：熔斷時 offline 若未送達 → 重啟後新進程 `_availability_cache = None` → `republish_availability()` 直接 return → 卡死設備永遠收不到有效幀 → 永不發 offline → **陳舊 `online` 永久存活** → 與新進程的 gateway `online` 同時成立 → HA 把陳舊數值顯示為「可用」。

**實證**：補一行後,殘留 `'online'` → `'offline'`,且 `_availability_cache = False` 使 MQTT 重連補發生效。

## 4. 重啟策略：uptime 守衛 + Docker arming 緩解

### 4.1 熔斷分支改造

```
_force_all_offline()                      # 既有函式，保留實體僅設 unavailable
if process_uptime > 300s:                 # 暫時性 → 值得試一次重啟
    CRITICAL(「解碼熔斷，保留 Discovery，交由 Docker 重啟」)
    if process_age < 10.0s:               # ✅ v2 新增：Docker arming 門檻
        await asyncio.sleep(10.1 - process_age)
    await asyncio.sleep(0.3)              # 給 offline publish 一個送出窗口
    os._exit(75)
else:                                     # 重啟後又立刻熔斷 = 持續性故障
    _decoding_disabled = True
    CRITICAL(「持續性故障，已鎖定解碼；實體與 WebUI 保留供診斷，請排查 adapter.feed()」)
```

**不得走 `gateway.stop()`** —— 它會對每台呼叫 `unregister_device()` → 清 Discovery（`src/main.py:351` → `:359`）,正是要避開的路徑。

`Dockerfile:6` 已有 `PYTHONUNBUFFERED=1`,故 `os._exit()` 不會吞掉最後那則 CRITICAL。

### 4.2 為何必須補 sleep（本次修訂的核心）

Docker 官方文件逐字：

> "A restart policy only takes effect after a container starts successfully."
> "...starting successfully means that the container is up for at least 10 seconds and Docker has started monitoring it."
> —— docs.docker.com/engine/containers/start-containers-automatically/

自然週期為啟動約 5s + 3×2s 熔斷約 6s ≈ **11s**,僅略高於門檻,屬**臨界值** —— 啟動加快或熔斷提前即落入 <10s 區間,屆時 restart policy **不生效**,容器直接停死、**WebUI 一併消失**。那比迴圈更糟。

補 sleep 至 10.1s 可完全消除此風險。**重啟次數上界為 1 次**（uptime < 300s 即鎖定）,故不會形成無限迴圈。

### 4.3 uptime 守衛的四情境

| 情境 | uptime | 走向 | 是否正確 |
|---|---|---|---|
| 冷啟動即持續故障 | < 5 min | 鎖定 | ✅ 重啟救不了持續故障 |
| 運行數小時後暫時性卡頓 | > 5 min | 退出→重啟→恢復 | ✅ |
| 運行數小時後真卡死 | > 5 min | 退出→重啟 | ✅ 先試一次 |
| ↑ 重啟後又立刻熔斷 | < 5 min | 鎖定 | ✅ 收斂,不進入迴圈 |

015 指出 `start_time` 每個新 `EdgeGateway` 都重設（`src/main.py:169`）—— 描述正確,但守衛要回答的是「值不值得試一次重啟」,非「故障何時開始」;四情境全部導向正確結果。

## 5. 為何不採 015 的 Host 持久計數

015 的機制**可行**（`report/016` F/G/H 三組以其原型跑通),但：

| | 本建議案 | 015 Host 計數 |
|---|---|---|
| 程式碼量 | ~40 行 | ~90 行 + 狀態檔 + 鎖檔 |
| 新增持久狀態 | 無 | 有（毀損／不可寫／計數污染 三種新故障面） |
| 需要解鎖程序 | 否 | **是**（目前尚未定義） |
| 自動重啟上界 | 1 次 | 2 次 |
| 跨 host reboot 保持計數 | 否 | 是 |
| **外部可觀測行為** | — | **等價** |

多換到的只有「多一次重啟嘗試」與「跨 host reboot 保持」,代價是一整套持久狀態機制。以本專案標準（單人維運、核心要求為 WebUI 不死）不划算。

**若仍決定採 015**,其條件必須全數落實,並補上 `report/016` §5 的 N1–N3（health 鎖定欄位、解鎖機制、計數過期）。

同時記錄 015 已排除的三項實作陷阱（`report/016` 已取得 errno 級實證）：

- `/tmp` 於本機為 **tmpfs**,reboot 必然全失 → 不可存放跨重啟計數
- 單檔 bind mount 上 `os.replace()` 必然失敗（`OSError errno=16 EBUSY`）→ 計數永遠寫不進去
- `on-failure:2` 會讓容器第三次停死、WebUI 一併消失 → 與目標相反

## 9. 殘餘風險

1. **已卡死的 worker 無法回收**（最多 3 個,為熔斷門檻）。non-daemon thread,直譯器退出前會 `join`,優雅關機仍可能等到 Docker grace period 用完被 SIGKILL。此為 Python 硬限制,`listen_master.py` V1.13 的關機診斷即為此而設。任何非子行程方案皆無法消除。

2. **300 秒門檻為可調參數**,須遠大於「啟動 + 熔斷」單次週期（約 11s）。建議設為具名常數並註解說明,而非硬編字面值。

3. **`os._exit(75)` 會略過 `stop()`**：不執行 MQTT flush 與 driver 關閉。USB FD 由 OS 於進程結束時回收;MQTT LWT（`src/main.py:765`）會觸發 gateway `offline`,使實體於重啟窗口內顯示 unavailable —— 預期且正確。

4. **MQTT 於熔斷當下不可用時**：`_force_all_offline()` 與重啟後的初始 `set_availability(False)` 皆會失敗,但 `_availability_cache` 已為 `False`,MQTT 重連時 `republish_availability()` 會補回 `offline`。**前提是 HAManager 未被銷毀** —— 這是不可再呼叫 `unregister_device()` 的另一個理由。

5. **鎖定狀態在 health 上不可見**：現行 health payload（`src/main.py:558`）僅有 `uptime_s`／`cmd_queue_size`／`devices`／`quarantined`／`health_publish_failures_total`,無鎖定欄位。鎖定後設備只是 `offline`,與「單純沒收到資料」外觀相同。**建議一併增補 `listen_decoding_locked` 欄位**（約 2 行）。

6. **沙箱驗證的固有限制**：以逐字複製件 + Mock 驗證行為語意,**未在整合執行期實測**。

7. **本專案現行環境無法實機驗收**：`profile/config.yaml` 中 `mode: listen` 設備數為 **0**,`ListenMaster` 根本不會被建立。真正的實機驗收必須在 py_jkbms 進行。
