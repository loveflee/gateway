## 但它沒看到一個坑:**重啟迴圈**

`os._exit(75)` → Docker 重啟 → 新進程 → 收到 chunk → **又卡** → 3 次逾時(~6s) → 又 exit → 又重啟…

而且 Docker 的重啟退避有一個關鍵行為:**容器成功運行超過 10 秒就會重置退避計時**。而這裡是啟動 ~5 秒 + 熔斷 ~6 秒 ≈ **11 秒 > 10 秒** → 退避永遠累積不起來 → **緊迫的無限重啟迴圈**。

後果:
- WebUI 每 11 秒閃一次,**你的救援機制在崩潰迴圈中無法使用** —— 這正是這幾輪一直在修的那個陷阱
- BMS 資料狂閃 online/offline
- 如果哪天合併部署,逆變器也一起陪葬

報告的前提是「2 秒不回應=卡死」。但**真卡死的話,重啟解決不了** —— 新進程一樣會卡。重啟只對「偶發系統停頓」有效。

---

## 我的改良:用 uptime 當守衛,不需要持久化計數器

```
熔斷觸發
  ├─ uptime > 5 分鐘  → 判定「偶發」→ _force_all_offline() → sleep 0.3s → os._exit(75)
  │                                    → Docker 重啟 → 卡死 thread 隨 OS 回收 → 自動恢復 ✅
  └─ uptime < 5 分鐘  → 判定「重啟後又立刻熔斷 = 持續性故障」
                        → _force_all_offline()
                        → 設 _decoding_disabled = True（停止再送 job，不再燒 worker）
                        → CRITICAL：持續性故障，已停止解碼，保留實體與 WebUI 供診斷
                        → 進程繼續活著 ✅
```

**兩條路徑都不呼叫 `unregister_device` / `send_discovery(cleanup=True)`** → HA 實體永遠不會被刪除,只會變 unavailable。

效果:

| | 現況 | 報告方案 | 我的改良 |
|---|---|---|---|
| HA 實體 | **被刪除** | 保留 | 保留 |
| 偶發卡頓 | 需人工重啟 | 自動恢復 | 自動恢復 |
| 永久卡死 | 空轉但穩定 | **無限重啟迴圈** | 重啟一次後停在可診斷狀態 |
| WebUI | 活著 | 崩潰迴圈中不可用 | 永遠活著 |

需要多加的只有 `_decoding_disabled` 旗標(否則 fallback 路徑會繼續送 job 把 4 個 worker 燒光)。總計比報告的方案多約 10 行。
