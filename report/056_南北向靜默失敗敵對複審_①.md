# 056 南北向靜默失敗敵對複審（第①題）

## 給非工程師的白話結論

這台閘道不是「設備壞了就會完全沒反應」的系統：串口／TCP timeout、壞封包、錯格式指令、指令佇列滿，大多已有 error 或 warning。本次重新審的是更危險的情況：**設備或 HA 畫面看起來正常，實際上中間那一段訊息已經沒送到，網關卻沒有把它當失敗。**

目前可證明會發生的問題有六類。最嚴重的是 MQTT：

* broker 拒絕訂閱控制指令時，HA 仍顯示按鈕，按了卻永遠不會寫到設備；gateway 沒有讀 broker 的拒絕回覆。
* MQTT state 發不出去時，設備仍被計為 ONLINE；HA 留著舊數字。
* availability 發送剛好失敗時，網關內部已認定 ONLINE，但不會為同一個 ONLINE 狀態補送；HA 可能長時間停在舊狀態。

這不是宣稱現場正在發生。本機沒有 broker ACL 拒絕紀錄、也沒有現場 MQTT 斷線時段可以對照；但本報告的隔離測試與容器內實際 Paho 原始碼已證明，**下列觸發條件一旦出現，程式控制流必然走到資料遺失或狀態分叉。**

本報告只回答第①題。未修改 production、profile、Docker；未審第②～④題。

## 基線、範圍與驗證

* 基線：`HEAD=1f38096`，以目前 working tree 為準。審查開始時已有未提交的 `adapter_helper.py`、`generic_adapter.py`、`config.yaml`、`bus_master.py`、`ha_manager.py`、`main.py`、`mqtt_client.py`；全部保留未改。
* 目前 runtime config：四台 active Solis、`poll_interval: 6`、log level `INFO`。
* 上行路徑：Driver RX → `BusMasterScheduler._process_poll()` → Adapter decode → `HAManager.publish_state()` → Paho → HA。
* 下行路徑：HA command topic → Paho callback → `_cmd_queue` → `submit_write()` → Driver ACK → verify read → state publish。
* 隔離重現：假 MQTT 固定回 `rc=4`，假 Driver／Adapter 不連任何現場設備。結果：

  ```text
  A bus_online=True successes=3 state_attempts=3 availability_attempts=1 availability_cache=None
  B discovery_latch=True calls_first=1 calls_after_retry=1
  C first=True second=False mqtt_calls=1 cached=2
  ```

* Runtime library 反查：`docker exec ginlong` 讀取容器內 Paho `Client.subscribe()`／`Client.publish()` docstring 與原始碼。它明定：
  * `subscribe()` 的立即 `rc` 只代表 client 是否連線／送出請求；用 `on_subscribe()` 及 `mid` 才能追 broker 的 SUBACK。
  * `publish()` 回傳 `MQTTMessageInfo`；需 `wait_for_publish()` 或 `on_publish()` 追送出完成。程式目前只讀 `rc`。

## 敵對發現

### F1 — P1：broker 拒絕 command subscription，HA 控制存在但寫入永遠不會發生

* **位置**：[src/mqtt_client.py:47](../src/mqtt_client.py#L47)-[49](../src/mqtt_client.py#L49)、[src/mqtt_client.py:81](../src/mqtt_client.py#L81)-[95](../src/mqtt_client.py#L95)、[src/mqtt_client.py:97](../src/mqtt_client.py#L97)-[119](../src/mqtt_client.py#L119)、[src/main.py:341](../src/main.py#L341)-[347](../src/main.py#L347)。
* **觸發條件**：MQTT 連線與 CONNACK 成功，但 broker ACL 對 `py_ginlong/+/+/set/+` 或 `py_ginlong/system/set/restart` 回 SUBACK failure。例如帳號可發布 Discovery，卻沒有訂閱 command topic 的權限。
* **會怎麼炸**：程式只檢查 `client.subscribe()` 的立即 `rc`，沒有設定 `client.on_subscribe`，也沒有按 `mid` 接收 SUBACK。Paho runtime 原始碼明示立即回傳不是 broker acceptance。Discovery 照常發布，因此 HA 的 switch／number／button 仍會出現。
* **後果**：HA 已把 command 發給 broker，但 gateway 從未收到它；[src/main.py:415](../src/main.py#L415)-[425](../src/main.py#L425) 與 [src/main.py:427](../src/main.py#L478) 不會被走到，設備完全不會寫入。
* **使用者能否察覺**：HA 顯示控制介面但按鈕無效；**沒有「broker 已拒絕訂閱」的 docker log**。只有立即 `rc` 失敗才會有既有 ERROR，那不是 SUBACK failure 分支。
* **性質／信心**：**實際可發生的 ACL 場景，信心高**；沒有現場 ACL 拒絕證據，故不宣稱現場正在發生。

### F2 — P1：state MQTT publish 回失敗，主動輪詢仍把設備記為成功與 ONLINE

* **位置**：[src/ha_manager.py:121](../src/ha_manager.py#L121)-[141](../src/ha_manager.py#L141)、[src/ha_manager.py:223](../src/ha_manager.py#L223)-[245](../src/ha_manager.py#L245)、[src/bus_master.py:390](../src/bus_master.py#L390)-[398](../src/bus_master.py#L398)。
* **觸發條件**：設備有正常 RX、Adapter 解碼得到非空 dict，但 Paho publish 回非零 `rc`（未連線、client 送出佇列滿、socket 已失效而 client 拒絕 publish）。
* **會怎麼炸**：`publish_state()` 會正確回 `False`，但 [src/bus_master.py:397](../src/bus_master.py#L397) 忽略它，下一行仍 `_record_success()`。連續兩次後 [src/bus_master.py:463](../src/bus_master.py#L463)-[465](../src/bus_master.py#L465) 將設備改為 ONLINE。
* **後果**：設備資料已到 gateway、沒有到 HA；HA 是舊 state，gateway health 仍是 success／ONLINE。這是資料遺失加健康狀態不同步。
* **使用者能否察覺**：單筆會有 `publish rc=...` WARNING，但上層不採用失敗返回值；因此是**有低層 warning、上層仍成功誤判**，不是完全無 log。
* **隔離證據**：假 MQTT 固定回 `rc=4` 後，三次輪詢結果為 `bus_online=True successes=3 state_attempts=3`。
* **性質／信心**：**已以目前 source 隔離重現，信心高**；現場觸發頻率未量測。

### F3 — P1：availability 發送失敗後，V3.0.11 的 rollback 仍不會補送同一狀態

* **位置**：[src/ha_manager.py:247](../src/ha_manager.py#L247)-[273](../src/ha_manager.py#L273)、[src/bus_master.py:454](../src/bus_master.py#L454)-[465](../src/bus_master.py#L465)；監聽軌同形態出現在 [src/listen_master.py:364](../src/listen_master.py#L364)-[371](../src/listen_master.py#L371)、[src/listen_master.py:416](../src/listen_master.py#L416)-[419](../src/listen_master.py#L419)。
* **觸發條件**：設備累積到 ONLINE（或 OFFLINE）門檻時，那一次 retained availability publish 回非零 `rc`。
* **會怎麼炸**：`set_availability()` 失敗後把 `_availability_cache` 回復為前值；初始情況前值是 `None`。但 BusMaster 已先在 [464](../src/bus_master.py#L464) 設 `state['online']=True`，以後成功輪詢不再走 `if not state['online']`，所以不會再次呼叫 `set_availability(True)`。監聽軌的補送條件只接受 cache **恰為** `False`，`None is False` 為假，也不會補送。
* **後果**：gateway 內部顯示 ONLINE，HA availability 留在 broker 上一次 retained 值或沒有值。只有之後真的反向變成 OFFLINE／再 ONLINE，或 MQTT reconnect 的再發布剛好成功，才可能修正。
* **使用者能否察覺**：第一次 publish 有 WARNING；之後「不會重試同一個 ONLINE」沒有 log。HA 畫面與 health 可長期互相矛盾。
* **隔離證據**：假 MQTT 固定回 `rc=4`，三次成功輪詢後得到：`bus_online=True ... availability_attempts=1 availability_cache=None`。也就是 ONLINE 已成立，但只有一次發送嘗試，沒有重試。
* **性質／信心**：**已以目前 V3.0.11 source 隔離重現，信心高**；不是上一版 cache 卡成錯值的舊問題，而是新 rollback 沒有建立重試觸發點。

### F4 — P2：Discovery 任一 publish 失敗，程式仍鎖成「完成」且下一次正常呼叫不重送

* **位置**：[src/ha_manager.py:143](../src/ha_manager.py#L143)-[189](../src/ha_manager.py#L189)、[src/ha_manager.py:218](../src/ha_manager.py#L218)-[221](../src/ha_manager.py#L221)、[src/main.py:390](../src/main.py#L390)-[410](../src/main.py#L410)。
* **觸發條件**：啟動／MQTT 重連的 Discovery 期間，任何 retained config publish 回非零 `rc`。例如 Paho outgoing queue 已滿或 client 暫時不可用。
* **會怎麼炸**：`send_discovery()` 在 [149](../src/ha_manager.py#L149)-[150](../src/ha_manager.py#L150) 先把 `_discovery_sent=True`，後續所有 `_safe_publish()` 的回傳值都被忽略，最後仍印「Discovery 完成」。下次一般呼叫在 [144](../src/ha_manager.py#L144)-[145](../src/ha_manager.py#L145) 直接 return。
* **後果**：HA 可缺少部分或全部 entity config；網關卻把 Discovery 當完成。要等下一次 MQTT reconnect 觸發 `reset_discovery()` 或進程重啟才會再送。
* **使用者能否察覺**：失敗 topic 有 WARNING，但「Discovery 完成」仍會出現，沒有失敗彙總、沒有重送任務。
* **隔離證據**：假 MQTT 回 `rc=4`，第一次 Discovery 後 `discovery_latch=True`；第二次 `send_discovery()` 的 publish 次數不變（`calls_first=1 calls_after_retry=1`）。
* **性質／信心**：**已隔離重現，信心高**。四台約 204 則 Discovery 未必會填滿 1000 筆 Paho queue，因此是否常見取決於 broker／斷線時序；未觀察到現場實例。

### F5 — P2：寫入 verify 成功但撞上 200 ms state 節流，HA 不會收到該次確認

* **位置**：[src/ha_manager.py:238](../src/ha_manager.py#L238)-[245](../src/ha_manager.py#L245)、[src/bus_master.py:311](../src/bus_master.py#L311)-[315](../src/bus_master.py#L315)。
* **觸發條件**：一筆 HA write 的 ACK 與 verify read 都成功，且 verify result 距上一次同設備 state publish 小於 0.2 秒。當輪詢剛發布，使用者立刻調整 number／switch，且 write 優先執行時即可命中。
* **會怎麼炸**：`publish_state()` 先把 verify 到的新值寫進 `_state_cache`，再在 [240](../src/ha_manager.py#L240)-[242](../src/ha_manager.py#L242) 無 log 回 `False`。BusMaster 不檢查返回值，仍在 [314](../src/bus_master.py#L314) 印「寫入驗證成功」。
* **後果**：設備已變更，HA 沒收到本交易的 state；目前設定下一次正常輪詢約 6 秒後才可能以快取補送。若這 6 秒內開始連續通訊失敗，HA 會維持舊值。
* **使用者能否察覺**：**沒有節流丟棄 log**；只看得到「寫入驗證成功」，畫面可能短暫沒有變。
* **隔離證據**：連續呼叫 `publish_state({'setpoint': 1})`、`publish_state({'setpoint': 2})` 得到 `first=True second=False mqtt_calls=1 cached=2`。
* **性質／信心**：**已隔離重現，信心高**；屬時序型短暫資料不同步，不是持續性故障。

### F6 — P2：state topic 使用 QoS0，`rc=0` 仍不代表 broker 或 HA 收到

* **位置**：[src/ha_manager.py:244](../src/ha_manager.py#L244)-[245](../src/ha_manager.py#L245)、[src/mqtt_client.py:73](../src/mqtt_client.py#L79)。
* **觸發條件**：Paho 對 QoS0 state 的 `publish()` 已回 `rc=0`，但 TCP 連線在封包到 broker 前後斷開，或 broker 無法轉發給 HA。QoS0 沒有 broker ACK／重送。
* **會怎麼炸**：gateway 將 `rc=0` 當作 `publish_state=True`，但容器內 Paho runtime docstring 明確說 `MQTTMessageInfo.wait_for_publish()`／`on_publish()` 才能追完成；程式沒有使用它。對 QoS0 而言，即使送到 TCP socket 也沒有 broker receipt 保障。
* **後果**：一筆瞬時數值或狀態轉換可能消失，沒有 exception、沒有 log，BusMaster 仍記成功。下一筆輪詢多半會補最新快取；但已發生又消失的瞬時狀態不會回來。
* **使用者能否察覺**：通常只看到 HA 跳過一筆；沒有 gateway 診斷。
* **性質／信心**：**協定層確定、現場發生尚未量測，信心高**。它是 QoS0 的明確取捨，不是單純理論猜想。

## 第①題裁決

**FAIL：6 項。**

失敗核心不是 Modbus 收包或 command 格式，而是 MQTT 完成語意沒有一路傳回上層：subscription 沒有 broker acceptance、state publish 的失敗／節流沒有被主動軌採納、availability rollback 沒有同狀態重試、Discovery 的一次性 latch 把局部失敗偽裝成完成、QoS0 又沒有端到端送達證據。

本輪只交付敵對證據，不包含修法，也不授權任何 production 變更。
