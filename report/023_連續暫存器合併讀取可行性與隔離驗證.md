# 023 — 連續暫存器合併讀取可行性與隔離驗證

日期：2026-08-10  
範圍：S6-EH1P6K 的既有 15 條唯讀 Modbus 指令。  
結論：**可以合併，且隔離端到端驗證通過；但任何正式套用都必然改變 Modbus 請求數、封包大小與資料更新時刻，故不符合「對外可觀測性完全一致」的前提。本次未修改正式程式、設定或服務，也未停止 `docker compose ginlong`。**

## 結論與建議

最值得優先考慮的候選是將完全相鄰的 `read_energy2_a`、`read_energy2_b`、`read_energy2_c` 合併為一個 FC4 `33161–33180`、`count: 20` 的讀取。它不讀取任何額外暫存器，隔離測試中將一個輪詢週期從 15 次請求降為 13 次（-13.33%），且 52 個解碼輸出完全相同。

依上游 S6 hybrid map 的分組，另有三個較積極的候選；四組一起採用時可降至 10 次請求（-33.33%）。這些候選會穿越未使用／保留地址，雖然上游定義支持其同群組意義，仍**沒有**以本機實體逆變器的加大讀取回應驗證，不能直接套用。

以下任一合併均不是「無對外差異」：同一輪詢週期的 TCP/RTU 封包數、封包長度、命令 ID／日誌順序，以及個別感測值更新時刻都會改變。在目前刻意雙 master 的壓力環境，較長回應亦有較大的交錯／重組風險。因此本報告只交付候選、隔離驗證證據與核准後的實機驗收條件；**不提出正式變更。**

`read_settings`（FC3 `43000–43011`）本身已連續。`43110` 與 `43117–43118` 中間有六個未知地址，且上游也將它們分成不同群組；本次不建議合併這兩個 holding-register 讀取。

上游 S6 hybrid map 的相關分組可見於 [hybrid_sensors.py](https://github.com/Pho3niX90/solis_modbus/blob/master/custom_components/solis_modbus/sensor_data/hybrid_sensors.py)。上游的讀取器以 `(start_register, registrar_count)` 讀取整塊，並在可恢復的 Modbus 例外時分割區塊重試；這支持「以區塊讀取」的設計方向，但不是本機硬體接受任意跨越地址範圍的保證，見 [data_retrieval.py](https://github.com/Pho3niX90/solis_modbus/blob/master/custom_components/solis_modbus/data_retrieval.py)。該專案也明確提醒較快輪詢會增加 Modbus 負載，見 [專案 README](https://github.com/Pho3niX90/solis_modbus)。

## 為何不能只改 `count`

FC3／FC4 回應為 `slave, function, byte_count, data..., CRC`。合併後每個原感測器必須改指向新的命令 ID，並把其資料偏移重算為：

```
offset = 3 + 2 × (sensor_register - merged_start_register)
```

例如 `33177` 在新 `33161` 區塊中的資料位移是 `3 + 2 × 16 = 35`。若只把既有命令的 `count` 加大、沒有重綁命令 ID 與偏移，解碼器仍會從舊命令／舊位置取值，結果會錯置。一次 Modbus 請求也不等於硬體保證的原子快照；逆變器內部取樣時序未由公開資料證實。

## 隔離驗證

測試全數位於工作目錄的 [continuous_read](</root/Documents/Codex/2026-08-09/root-ginlong-master-1-2-report/test/continuous_read>)。測試程式使用正式檔案的唯讀副本：`generic_adapter.py`、`driver.py`、`map_validator.py` 與 Solis map；沒有 import 或寫入正式執行目錄。

測試以本機 `127.0.0.1` 假 Modbus 裝置回應固定暫存器值，經實際 adapter 產生請求、實際 robust driver 收發、CRC／回應長度檢核、解碼與 map validator 驗證。測試設定為 `inter_frame_delay=0`、`idle_timeout=0.1s`、`flush_max_time=0.2s`；因此時間只代表可重現的 loopback 相對基準，不可當作實體網路延遲承諾。

## 實機被動觀察與限制

已按提供的 [tcplog.sh](/root/py_ginlong/tcplog.sh) 進行短暫被動擷取；可看到正常形式的 FC3／FC4 RTU-over-TCP 請求與回應。不過管線中的 [l4.py](/root/test/l4.py) 會對**每一個 TCP segment**直接計算 RTU CRC，沒有依 TCP stream 重組。因此在雙 master 壓力流量下，TCP 分段或相鄰資料會被誤報為 CRC 不符。這是觀察工具的解析限制，不是逆變器、主站或雙 master 架構的缺失；雙 master 亦依任務說明視為刻意的穩定性測試情境。

為維持「對外可觀測性不變」，本次沒有向 `192.168.106.14:502` 送出任何候選的加大讀取，因此沒有實機 `33161–33180` 或 P2 範圍的接受／例外碼證據。直接送出此類請求即會改變可觀測的 Modbus 流量，違反本任務前提。

## 核准後才可進行的實機驗收

若之後明確核准「允許改變測試時段的 Modbus 流量」，應依下列順序執行，且僅在測試設定／測試副本中進行：

1. 先單獨驗證 P1 FC4 `33161, count=20`；確認每次回應資料長度恰為 `40` bytes、CRC 正確、無 Modbus exception，並比對 52 個輸出值。
2. 累積足夠週期（建議至少 500 次）後，才逐一加入 P2 的三個區塊；一次只增加一個，保留可立即還原的原始測試設定。
3. 使用可 TCP stream 重組的擷取／解析器，按連線與方向驗證完整邏輯訊框；不要將 `l4.py` 的單一 segment CRC 當作判定依據。
4. 在現有雙 master 壓力情境下，比較 timeout、例外回應、完整回應率、每輪資料新鮮度與對外輸出；若任一可觀測項目必須維持不變，則不得將合併方案套用到正式設定。
