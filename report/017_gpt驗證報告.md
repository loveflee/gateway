# 017 py_jkbms 熔斷復原重新驗證報告（更正版）

**日期：**2026-08-08　**結論：核心熔斷修正可採用；先前 TCP 截取結論撤回。**

## 更正與驗證範圍

前版錯把 `192.168.106.14:502` 的 TCP→RS485 流量當成 py_jkbms 證據，該段與本服務無關，已完全移除。本輪只驗證 `/root/py_jkbms`：Compose 以 host network 運行、直通 CP2102N USB serial-by-id（`docker-compose.yaml:5-28`），工作目錄為 `/app/profile`（`:17-24`），故 runtime 設定是 `profile/config.yaml`，不是根目錄 `config.yaml`。

現場唯讀核對：py_jkbms 正在監聽 **8002**、USB 已開啟、UID 0/1/2 已掛載；`py_jkbms/health` 的一次實收 payload 為三者 `online=true`、`listen_decoding_locked=false`、`quarantined=[]`、健康發布失敗數 0。WebUI traffic API 現已正確連至 8002；所有 serial bytes 都從這個既有 ring buffer 讀取，沒有另開或寫入 USB。

## 新風險

1. **中：Docker 10 秒補償是死碼。** `uptime < 10` 被放在 `uptime > 300` 分支內（`listen_master.py:295-315`），不可能執行。此刻 exit 只在 300 秒後，Docker 已 armed，故不阻礙復原；但原驗收的 age=3 補 sleep 結論不成立，應刪除死碼／補實際條件測試。
2. **中：重啟上界只適用同一連續故障。** 每次穩定超過 300 秒又熔斷仍會再 exit；沒有跨 process 的持久計數。應將文件改為「連續故障最多試一次重啟」。
3. **中：thread 無法被 timeout 殺死。** `wait_for` 取消不了已執行的 Python worker（`listen_master.py:108-125,273-291`）；鎖定只阻止後續提交，修好 adapter 後仍需重啟。請對 health 的 `listen_decoding_locked`（`main.py:578-584`）告警。
4. **低：runtime profile 只發布 UID 0–2，但 USB 總線也有 UID 3–9 遙測。** 這可能是刻意只管理三台，並非程式故障；若 3–9 也應上 HA，必須明確加入 profile，不能靠被動側錄自動掛載。UID 10–15 在本輪只有控制請求、未見 JK 遙測。

## 邊界

未修改 py_jkbms 程式、設定、Compose、容器或硬體。MQTT 僅做一次訂閱以讀 health；未發布。USB 只透過已開啟的 `/api/traffic` buffer 讀取。下列「TX」是由 CRC 通過的 Modbus `UID 0x10` 請求推論出的協定方向；程式實際將所有串口讀取標記為 `[Listen-RX]`（`listen_driver.py:249-264`），不提供硬體方向旗標。
