# 017 py_jkbms 熔斷復原獨立驗證報告

**日期：**2026-08-08　**標的：**`/root/py_jkbms` V1.14/V2.11　**結論：有限採用**

## 執行結論

核心修正可採用：隔離測試 **4/4 通過**，確認熔斷不清 HA Discovery、全設備 retained availability 轉 `offline`、晚期熔斷要求 Docker 以 exit 75 重啟、早期熔斷鎖定後不再提交解碼工作，正常有效幀仍可回復 `online`。現場容器亦確為 `restart=unless-stopped` 且運行中。

但不完全背書原驗收的「6/6」：其 V5（age=3 秒補 sleep）不可能走到實作中的退出分支。退出分支前提是 `uptime > 300`，內層卻判斷 `uptime < 10`，條件互斥；因此 10 秒補償是死碼。這次不會造成容器不重啟（真正退出時早已超過 10 秒），但應刪除或重構，避免日後誤改門檻時留下假保護。

## 新風險與處置

| 等級 | 風險／證據 | 影響與最小處置 |
|---|---|---|
| 中 | `if uptime < DOCKER_ARM_SECONDS` 被包在 `if uptime > 300` 內（`listen_master.py:295-315`）；與原報告 V5 的 age=3 秒結果矛盾。 | 現狀安全但測試覆蓋是假象。刪除內層補償及其宣稱，或把 arming 判斷置於真正可能 exit 的共同路徑；補一個實際條件測試。 |
| 中 | 「自動重啟上界 1 次」僅適用同一故障緊接重啟後再次熔斷；沒有跨行程持久計數。每次成功運行超過 300 秒後仍可再 exit 一次（`listen_master.py:293-320`）。 | 長期反覆、間歇性 adapter 問題可反覆重啟。應在操作文件以「每個連續故障事件最多一次」表述；若必須全域上限，才評估持久計數。 |
| 中 | `asyncio.wait_for()` 逾時不能終止執行中的 Python thread；三個已提交工作仍可能永久存在（`listen_master.py:108-125, 273-291`）。 | 鎖定確實阻止新增提交，卻不會自行恢復解碼；必須修 adapter 後重啟。此為既知限制，health 的 `listen_decoding_locked`（`main.py:578-584`）應納入告警。 |
| 低 | `os._exit(75)` 略過正常 stop/flush（`listen_master.py:313-316`）。 | offline QoS1 沒送達時，下一進程註冊會覆寫 offline（`listen_master.py:144-155`）；MQTT 重連亦會重發快取（`ha_manager.py:77-89`）。仍會有短暫的陳舊 online 視窗。 |
| 低 | 下列 tx/rx 截取的 163 個 CRC 失敗片段，是 TCP stream 被分段／合併後由 `l4.py` 逐 segment 當 RTU 幀解析的結果，**不是** USB/RS485 雜訊的已證明證據。 | 不可用此工具的 CRC 統計觸發熔斷或判硬體故障；若需診斷 TCP→RS485，應使用有 TCP reassembly 的解析器。JK adapter 本身以 buffer 切幀（`jkbms_adapter.py:311-355`）。 |

HA 外觀保持一致的依據：Discovery 只在 `send_discovery(cleanup=True)` 才清空 retained（`ha_manager.py:118-196`），熔斷路徑未呼叫它；availability 使用 gateway 與 device 的 `all` 模式（`ha_manager.py:265-269`）。D1 初連失敗不退出、交給 USB 退避重連，程式位置為 `main.py:739-759` 與 `listen_driver.py:225-252`。
