# 監聽熔斷原因白話說明

## 先說結論

**USB／串口不是「不能用」，也不是目前有證據支持的主要原因。**融斷計數只在「收到非空資料後，整批解碼超過 2 秒」時增加；USB 拔除、串口例外或沒有資料，走的是斷線／重連或離線判定路徑，不會累加解碼融斷計數。現行 `profile/config.yaml` 沒有任何 `mode: listen`，所以這個環境根本沒有建立 ListenMaster，也沒有實機證據可把問題歸咎 USB、JKBMS 或任一設備（`profile/config.yaml:22-46`）。

## 「三次、每次兩秒」到底是什麼

每次監聽收到一段資料（最多 1024 bytes），程式把這段資料交給一個背景 worker；worker **依序**問所有監聽 adapter：「這是不是你的封包？」。整批在 2 秒內沒有回來，就記一次逾時；累積到第 3 次才熔斷。任何一批在兩秒內結束，即使沒有解出資料，計數就歸零（`src/listen_master.py:197-245`）。

所以它不是「6 秒沒收到 USB 資料就熔斷」，而是「三段有資料的解碼工作都各自等超過 2 秒」。最快約 6 秒，但若封包之間隔很久，可能隔數分鐘才湊到三次。它以整批 adapter 為單位，不是以單一 UID 為單位；一個 adapter 卡住，所有監聽設備都會受影響（`src/listen_master.py:162-182`）。

## 已證實的程式事實

| 現象 | 程式實際做法 | 意義 |
|---|---|---|
| USB 斷線／拔除／串口錯誤 | `read_stream()` 拋 `DriverDisconnectError`；主迴圈強制 offline、等 1 秒後由 driver 退避重連 | 這不是解碼融斷（`src/listen_driver.py:225-270`；`src/listen_master.py:272-275`） |
| USB 沒有任何資料 | 單次讀取等 5 秒後回傳空資料，主迴圈休息 0.5 秒 | 不增加「1/3」計數；已上線設備會依 `offline_time` 變 offline（`src/listen_driver.py:249-266`；`src/listen_master.py:321-335`） |
| adapter 丟例外 | 例外被記錄為「Adapter 解析崩潰」，本批仍會結束 | 通常不熔斷；比較可能變成沒有效幀、之後設備離線（`src/listen_master.py:170-182`） |
| 真正熔斷 | 第三次整批超過 2 秒 | 現行程式會全設備 offline、解除註冊、清除 HA Discovery、重建 executor；HA 實體可能消失，不只是變灰（`src/listen_master.py:223-244`；`report/012_熔斷復原方案裁決.md:48-58`） |

USB 監聽有完整的開啟、EOF 偵測與重連實作；重連從約 1 秒開始、失敗時最長退避到 10 秒（`src/listen_driver.py:196-208,225-247`）。反而要注意：若 USB 在**啟動第一次**就連不上，現行 `main.py` 會直接退出，這是啟動可用性問題，也不是融斷（`src/main.py:695-731`）。

## 可能原因：依可信度排序

1. **某個 adapter 的 `feed()` 永久卡住或執行很久**：例如未來新增 adapter 引入無窮迴圈、鎖等待或同步外部 I/O。這最符合保險絲的設計目的；卡住的一次工作不能被 Python 安全中止，才需要在三次後停止繼續累積 worker（`src/listen_master.py:139-160`）。
2. **主機／容器暫停或 CPU 被占滿**：2 秒包含 worker 排隊、排程不到 CPU 與實際解碼時間。即使 parser 最後會結束，連續三次被嚴重延後也可觸發。這是由 `wait_for(..., timeout=2.0)` 的機制推得的合理風險，但目前沒有 CPU、Docker throttling 或實機 log 證據。
3. **資料流使 parser 工作量異常大，或未來 adapter 的邊界處理有缺陷**：雜訊、封包切段、惡意／異常長資料本身不必然融斷，但可能放大解析成本。單幀回傳超過 256 keys 會被丟棄；該保護發生在 adapter 已完成之後，救不了 adapter 自身卡住（`src/listen_master.py:252-263`）。
4. **目前 JKBMS parser 本身永久迴圈的可能性低**：現行 `feed()` 的分支不是刪除已處理／假表頭資料，就是 `break` 等下一段資料，且函式內沒有 socket、serial、sleep 或 lock（`adapters/jkbms_adapter.py:311-430`）。這不是「絕不可能超過兩秒」的實測保證；只表示從靜態程式看，沒有明顯無窮迴圈或外部阻塞點。

TCP 同理：TCP EOF、socket error 走 `DriverDisconnectError`，不是解碼融斷；只有收到資料後把 adapter 解碼拖超過兩秒，才會走保險絲（`src/listen_driver.py:140-161`；`src/listen_master.py:204-221`）。

## 看日誌怎麼分辨

| 看到的訊息 | 優先懷疑 |
|---|---|
| `Adapter 解碼超時 (1/3)`、`(2/3)`、`連續 3 次解碼逾時！保險絲熔斷` | adapter 卡住、CPU/排程嚴重延遲，或異常資料造成極慢解碼；不是單純「沒資料」 |
| `收到 EOF，USB 可能被拔除`、`串口實體異常`、`串口異常，…後嘗試重連` | USB、線材、供電、udev／設備拔插或串口被占用；不應有 1/3 計數 |
| `Adapter 解析崩潰` | adapter 解碼例外；檢查 traceback、輸入封包與 map，通常不是 fuse |
| `超過 60s 無有效封包，判定 OFFLINE` | 有 driver 但沒有有效可發布資料；可能是資料流、UID／profile／解析規則，不等於 USB 壞掉 |

`report/013_熔斷復原方案獨立驗證.md:21-29` 已獨立證實：真正要防的是 worker 卡住後持續提交工作，不是 USB 無資料。其 Mock 驗證可說明程式語意，不能替代 USB 現場診斷。

## 未被目前環境證明的事

尚未證明 USB 硬體故障、JKBMS parser 曾卡死、TCP/serial driver 曾觸發保險絲、或主機曾 CPU 飢餓；也沒有任何 listen 實機 log 可計算發生率。要判定根因，至少需要保留熔斷前後的上述日誌、主機 CPU／記憶體／Docker 限流資訊，以及原始 `[Listen-RX]` 資料片段；不要只看到「熔斷」就先換 USB 線。
