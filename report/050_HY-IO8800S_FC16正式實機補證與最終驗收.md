## 手冊與地址裁決

手冊 3.1.1 列出 Holding Register 可用 FC03／FC06／FC16；3.1.5 說明 holding parameters 均以 **big-endian** 讀寫。3.2.2.6 的範例讀 PLC `40045` 時送 `FC03 start=0x002c`，直接證實 protocol address 為 PLC address − `40001`（0-based）。

手冊 3.1.5.2 指出 Rule 1 起始於 PLC `40129`／`0x0080`，每組固定 16 bytes（8 registers），欄位順序為 mode、action、output、input、Param1、Param2；Param1 是 4-byte `uint32`。因此 Param1 位於固定 block 的第 4 register：

```text
40129 - 40001 = 0x0080     Rule1 start
0x0080 + 4 = 0x0084        Param1 start
0x0084 + 40001 = 40133     PLC address
```

表格跨頁的左欄文字在 DO/DI／Param rows 有排版合併，但不以那個視覺排版單獨判斷；以明示的 16-byte fixed layout、six-field order、FC03 base-address example 和下列全區段硬體 readback 交叉確認。手冊 3.2.2.8 的 FC16 例子也是 quantity=2、byte-count=4，ACK 僅 echo start/quantity。

手冊 2.4 同時警告：除了 serial/device address，其餘參數修改後立即生效。故只有在實機讀到 Rule1 `mode=0`（關）後才寫入；mode=0 沒有 Param1 operational range，測值只用來證明 32-bit packing，且都已回復。

## 唯讀硬體確認與安全基線

測試 profile 先以 host 和 container 的 `map_validator.py` 雙重 PASS，然後只暫把 UID3 profile 指向它並 restart。正式 Gateway 的正常 poll 取得：

```text
FC03 Rule1 block TX  00 05 00 00 00 06 03 03 00 80 00 08
FC03 Rule1 block RX  00 05 00 00 00 13 03 03 10
                      00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00

FC03 Param1 TX      00 06 00 00 00 06 03 03 00 84 00 02
FC03 Param1 RX      00 06 00 00 00 07 03 03 04 00 00 00 00

FC01 coils TX       00 04 00 00 00 06 03 01 00 00 00 08
FC01 coils RX       00 04 00 00 00 04 03 01 01 00
```

MBAP fields分別為 transaction id、protocol `0`、length、UID `3`、PDU。Rule1 raw registers `0x0080..0x0087` 全為零：mode/action/DO/input/Param1/Param2 = `0/0/0/0/0/0`。8 coils 與兩個 group 均為 OFF／`all_off`。故 restore value 是 `0x00000000`，且 disabled rule 不會因測試 Param1 觸發 relay action。

## FC16 隔離／敵對驗證

以目前 production source 重跑 `scratch/fc16_049_independent_review.py`：**308 PASS / 0 FAIL**，輸出在 `scratch/fc16_050_isolated_recheck.stdout`、摘要在 `scratch/fc16_050_isolated_summary.json`。

- `uint32` 的 `0`、`1`、`1000`、`100000`、`0x12345678`、`0xffffffff` 皆與 PyModbus 3.13 的 RTU PDU/CRC、MBAP request byte-for-byte 相同。
- strict FC03 verify 強制 quantity=2/4 bytes；first-word mismatch、second-word mismatch、short frame、wrong byte count、wrong word order、decode failure 與 timeout 全部零 success publish。
- TCP ACK guard：合法 FC05/06/15/16(q=1/q=2) PASS；wrong transaction/protocol/length/UID/FC/address/quantity、short/truncated/overlong frame 和 FC16 exception `0x90` 均 fail-closed。
- regression vector：FC06 `06 00 10 00 2A`、legacy FC16 `10 00 20 00 01 02 00 2A`、FC01 8 coils、FC05 CH1/CH8、FC15 group_01/group_234 全部 PASS。

資料流檢查結論：strict codec 的 FC03 decoder 要求完整 4-byte chunk；無法解碼會 raise，空 result 會被 `decode()` 拒絕。因而 BusMaster 的 legacy `None` 相容分支對此 strict FC16 route 不可達。mock 的 low/high-half mismatch、malformed response、timeout 都沒有 `publish_state`；**DATA FLOW BLACK HOLE = NONE**。

實機 regressions 也走 MQTT closed loop：

```text
FC05 ON   Write PDU 05 00 00 FF 00  → FC01 q=1 RX 01 01 01
FC05 OFF  Write PDU 05 00 00 00 00  → FC01 q=1 RX 01 01 00
```
