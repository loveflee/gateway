## 3. 第二節：FC15 協定層敵對驗證

### 3.1 RTU FC15 對 PyModbus oracle

七組向量，production encoder 產出的完整 RTU 幀（含 CRC）**逐位元組等於** PyModbus `WriteMultipleCoilsRequest` 經 `FramerRTU` 產生的幀：

| 向量 | production RTU 幀 | PyModbus oracle | 判定 |
|---|---|---|---|
| 2 coils @0 = `11` | `03 0F 00 00 00 02 01 03 1F 4F` | 相同 | PASS |
| 3 coils @2 = `101` | `03 0F 00 02 00 03 01 05 B7 4D` | 相同 | PASS |
| 4 coils @4 = `1101` | `03 0F 00 04 00 04 01 0B 0F 48` | 相同 | PASS |
| 8 coils @0 = `10101010` | `03 0F 00 00 00 08 01 55 BF 73` | 相同 | PASS |
| 9 coils @0（跨 byte） | PDU `0F 00 00 00 09 02 55 01` | 相同 | PASS |
| 16 coils @0 | 相同 | 相同 | PASS |
| 17 coils @10（跨 3 bytes） | 相同 | 相同 | PASS |

逐欄位另行驗證（UID / FC=0x0F / start / quantity / byte count / 幀長）與 LSB-first packing（含**未使用高位必須為 0**）—— 七組全部通過。CRC 由本檔自寫的 CRC16 獨立重算，與 production 一致。

### 3.2 MBAP FC15

七組向量的 MBAP 幀同樣**逐位元組等於** PyModbus `FramerSocket` 輸出（transaction ID 對齊後比較）。protocol ID = `0x0000`、MBAP length 與實際載荷一致、UID 正確、FC = 0x0F 全部逐項驗過。

**RTU 與 MBAP 的 PDU 完全相同** —— 兩者共用 `GenericAdapter.build_fc15_pdu()`，這是正確的架構（transport-neutral PDU + 各自框架），不是兩份重複實作。連續 5 筆 FC15 的 transaction ID 遞增不重複。

### 7.1 黑洞 G：群組狀態發布假值（FOUND）

**群組狀態只在「群組寫入的 verify」時被計算，輪詢路徑（poll）完全不重算它**；而 `ha_manager` 的 state 快取會把舊值合併進**每一次**發布。結果是：一旦有人單獨動了群組裡的某一路（FC05 單路開關、外部控制、設備自身狀態改變），群組值就開始說謊，並且每次輪詢都重播一次。

實機重現（重啟後乾淨環境，21:26:57 起）：

```
21:26:57  {... 全部 OFF ...}                                   ← group_234 不存在（尚無群組寫入）
21:27:03  {... 全部 OFF ..., "group_234": "all_off"}           ← 下 group_234=all_off，建立群組值
21:27:09  {"switch_2": "ON", ..., "group_234": "all_off"}      ← ★ 同一則 JSON 自相矛盾
21:27:12  {"switch_2": "ON", ..., "group_234": "all_off"}      ← ★ 再次重播同樣的假值
21:27:17  {... 全部 OFF ..., "group_234": "all_off"}           ← 復原
```

`group_234` 的成員是 `switch_2/3/4`，`all_off` 的向量是 `[OFF, OFF, OFF]`。實際板況是 `[ON, OFF, OFF]`。**Home Assistant 上的「Relay Group 234」下拉選單顯示「all_off」，而第 3 路繼電器是閉合的。**

同一現象在 21:21:29／21:21:30 也發生過一次（`switch_0: ON` + `group_01: all_off`），共兩次獨立重現。

**這不是寫入路徑的 silent success** —— 寫入路徑是乾淨的（7 節其餘 8 項全封閉）。這是**對外可觀測性的假狀態**：網關持續向 HA 發布一個與實際 coil 狀態矛盾的群組狀態。依第六節規則「黑洞 G：錯誤狀態仍 publish 給 HA」→ **DATA FLOW BLACK HOLE = FOUND**。

嚴重性：FC15 群組功能的存在理由就是「一組繼電器要一起看、一起切」。操作員在畫面上讀到「全關」而實際有一路通電，正是這個功能最不能出的錯。ATS 類用途尤其致命。

**必須說清楚界線：**

- 成立：**本 Gateway 內部**不允許自己的其他 poll／write 插入單次 write→verify 循環。
- 成立：FC15 證明多個 coils 在**同一筆 Modbus request** 中提交。
- **不成立**：這不是 Modbus／RS485 世界的 global atomic transaction，擋不住外部 master。
- **不成立**：這不表示機械繼電器接點在同一微秒動作。**ATS 等安全互鎖用途仍必須有硬體 interlock。**

## 14. 缺陷、根因與最小修改（不施工）

### 14.1 缺陷 1（阻擋放行）：群組狀態在輪詢路徑不重算，持續發布假值

- **證據**：第 7.1 節，實機兩次獨立重現。同一則 MQTT payload 同時含 `switch_2: "ON"` 與 `group_234: "all_off"`。
- **根因**：
  1. `adapters/generic_adapter.py` 的 `_extract_data()` 在 `ctx_type == "poll"` 分支只解 `sensors`，**完全不碰 `coil_groups`**；群組值只在 `ctx_type == "verify"` 且 `context["coil_group"]` 存在時才被計算。
  2. `src/ha_manager.py` 的 state 快取會合併歷史 key，因此那個過期的群組值會**隨每次輪詢重新發布**，而不是自然消失。
- **最小修改位置（單一模組）**：`adapters/generic_adapter.py`，`_extract_data()` 的 poll 分支，在 sensor 迴圈**結束之後**加入：對 `self.coil_groups` 中 `verify_command_id == cmd['id']` 的每個群組，設 `result[group_key] = self._match_coil_group_state(group, result)`。
  - 直接重用既有的 exact matcher，不新增比對邏輯。
  - **不需要動 `bus_master.py`、`ha_manager.py`、`driver.py`。**
- **同一輪必須一併處理的連帶影響**：修好之後，任何不對應命名 vector 的板況會讓群組值變成 `__UNMATCHED__`，而 HA 的 `select` 收到不在 `options` 內的值會報錯。因此 `profile/relay_8ch_map2.yaml` 必須二選一：
  - (a) 在 `B2_SETTING` 的 `options` 中加入對應的哨兵選項；或
  - (b) 把群組狀態顯示改成獨立的 `sensor` 實體，`select` 只當命令入口（`ha_manager` 已支援 `state_key`／`link_b1` 的重導）。
  - 這是 profile 的設計決策，**應由施工者決定，我不代為選擇**。

### 14.2 缺陷 2（非阻擋，須清理）：clean-up 未完成

`profile/relay_8ch_map2_4ch_test.yaml`、`profile/relay_8ch_map2_8ch_test.yaml` 是 041 實機測試用的暫時 profile，仍留在 rw 掛載的 `profile/`。它們會出現在 WebUI 的 profile 下拉選單，可能被誤選（誤選 8ch_test 會讓 8 路全部進同一群組）。建議移出 `profile/` 或改用被 gitignore 的命名慣例。

### 14.3 觀察 1（非缺陷，須文件化）：exception ACK 現在會走「設備邏輯拒絕」分支

新 guard 讓 native TCP 的 Modbus exception 正確回 `False`。而 `bus_master._process_write()`（禁改檔案，行為既有）對 `ack is False` 的處理是：記 WARNING「設備邏輯拒絕」→ `_record_success(uid)` → **不重試、不 verify、不 publish**。

- 這**不是** false publish（HA 不會收到假狀態），也不是靜默（有 WARNING）。
- 但這是 native TCP 首次能走到的分支（施工前 exception 被盲收成 `True`，會繼續走 verify → 不符 → 重試）。**行為變了，而且是變正確**，與 RTU driver 的既有語意一致。
- 建議：在 `CLAUDE.md`／`AGENTS.md` 明記此語意，避免日後被誤判為 bug。

### 14.4 觀察 2（潛在，目前不可觸發）：`_pending_group_states` 從不清除

`_prepare_coil_group_write()` 寫入 `self._pending_group_states[key]`，但成功或失敗後都**不清除**。目前不可利用 —— `build_verify_read()` 只在 `_process_write()` 內、同一次 attempt 中緊接 `encode_write()` 之後被呼叫。但這是一個潛在的 fail-open 面：任何未來新增的呼叫端若單獨呼叫 `build_verify_read(group)`，會拿到上一次的 pending state 而非拒絕。建議在終局（成功／耗盡）清除，或改為單次消費（pop）。
