# 055 南北向靜默失敗敵對審查（第①題）

## 白話結論

這套程式平常可以輪詢設備、把數值送到 Home Assistant；本次沒有發現「設備回覆正常卻整台資料完全消失且毫無紀錄」的既有路徑。不過它有幾個會在 MQTT 短暫故障或權限設定錯誤時**說自己成功、畫面卻沒真的同步**的洞。

最危險的兩種畫面如下：

1. 設備明明有回覆，網關也把它判為 ONLINE，但 MQTT 這一筆沒有送出去；HA 會保留舊數值，health 仍可能顯示設備健康。
2. HA 控制按鈕仍會出現，但 broker 若拒絕 gateway 訂閱指令 topic，按鈕送出的指令根本不會進入 gateway，docker log 也沒有「broker 拒絕訂閱」這條原因。

這不是說目前現場已在發生：本機沒有 broker ACL、Paho callback 或現場 log 可證明它正在觸發。但程式碼與隔離重現已證明：只要符合下述條件，結果必然發生。此報告只審第①題，未進入第②～④題，也沒有改 production、profile 或 Docker。

## 審查基線與方法

* 基線：working tree 的 `HEAD=1f38096`，並以當前未提交版本為真相來源。
* 當前 runtime 設定：[profile/config.yaml](../profile/config.yaml) 為四台 active Solis、`poll_interval: 6`、根 logger 為 `INFO`。
* 審查路徑：
  * 上行：Driver RX → `BusMasterScheduler._process_poll()` → Adapter decode → `HAManager.publish_state()` → Paho MQTT → HA。
  * 下行：HA command topic → Paho callback → asyncio command queue → `submit_write()` → Driver ACK → verify read → state publish。
* 隔離重現：使用假 MQTT（`publish()` 回傳非零 `rc`）與假 Driver／Adapter，不連線 broker、不連設備、不寫入檔案。重現結果：

  ```text
  discovery_latch True calls_first 1 calls_after_second 1
  availability_cache True calls_first 1 calls_after_second 1
  poll_state True success_count 2 publish_calls 2
  first=True second=False mqtt_calls=1 cached_setpoint=2
  ```

`poll_state=True` 代表兩次設備輪詢都被 scheduler 計為成功，即使兩次 MQTT publish 都回非零 rc；這不是推測。

## 發現清單

### F1 — P1：broker 拒絕訂閱時，HA 控制介面存在但指令通道已死

* **位置**：[src/mqtt_client.py:47](../src/mqtt_client.py#L47)、[src/mqtt_client.py:81](../src/mqtt_client.py#L81)-[95](../src/mqtt_client.py#L95)、[src/mqtt_client.py:97](../src/mqtt_client.py#L97)-[119](../src/mqtt_client.py#L119)、[src/main.py:341](../src/main.py#L341)-[347](../src/main.py#L347)。
* **觸發條件**：MQTT TCP 連線與 CONNACK 成功，但 broker ACL 對 `py_ginlong/+/+/set/+` 或 `py_ginlong/system/set/restart` 回 SUBACK failure／拒絕 QoS。例如 broker 帳號可 publish Discovery、但沒有 subscribe command topic 的權限。
* **為何會炸**：`subscribe()` 檢查的是 `client.subscribe()` 的立即 `rc`，它只表示 Paho 是否接受／排入送出 SUBSCRIBE；程式沒有設定 `client.on_subscribe`，因此不會讀 broker 後續 SUBACK 的授權結果。程式接著照常送 Discovery，HA 仍會顯示 switch／number／button。
* **後果**：HA 指令會發布到 broker，但 gateway 從未訂閱成功，`_on_mqtt_message()`、`_mqtt_consumer_task()`、`BusMasterScheduler.submit_write()` 均不會被呼叫。設備不會寫入，HA 端沒有 gateway 回覆；若原值不變，看起來就是「按了沒反應」。
* **可察覺性**：**無 docker log**（除非立即 `rc` 本身失敗；SUBACK 拒絕不是這條分支）。HA 仍有實體，誤導性高。
* **信心**：**高**（標準 MQTT/Paho 非同步訂閱契約與 callback 缺失）；**尚未觀察到現場 broker 正在拒絕**。

### F2 — P1：上行 state publish 失敗仍把設備判為通訊成功

* **位置**：[src/ha_manager.py:96](../src/ha_manager.py#L96)-[116](../src/ha_manager.py#L116)、[src/ha_manager.py:198](../src/ha_manager.py#L198)-[220](../src/ha_manager.py#L220)、[src/bus_master.py:372](../src/bus_master.py#L372)-[380](../src/bus_master.py#L380)。
* **觸發條件**：串口／TCP 設備回覆與 Adapter 解碼都成功，但 `self.mqtt.publish()` 回傳非零 `rc`。實際例子是 Paho 尚未連線、送出佇列滿，或 client 已在連線中斷邊緣而拒絕此 publish。
* **為何會炸**：`HAManager.publish_state()` 正確回傳 `False`；但 `_process_poll()` 在 [src/bus_master.py:379](../src/bus_master.py#L379) 不檢查它，下一行仍執行 `_record_success()`。兩次這種輪詢後，[src/bus_master.py:436](../src/bus_master.py#L436)-[447](../src/bus_master.py#L447) 會將設備轉 ONLINE。
* **後果**：資料已到網關、但未到 HA；HA 留著上一次 state，而 gateway health／availability 可顯示該設備 ONLINE。若隨後五次輪詢失敗，HA 最終只會收到 offline，最後一筆設備數值仍是舊的。
* **可察覺性**：有單筆 WARNING：`publish rc=...`，但**沒有把 MQTT 發布失敗反映到呼叫端、設備健康度或重送狀態**；上層仍以通訊成功處置。故屬「半靜默成功誤判」，不是完全無 log。
* **隔離證據**：假 MQTT 固定回 `rc=4` 時，連續兩次 `_process_poll()` 的結果為 `online=True, success_count=2`，同時兩次 state publish 均失敗。
* **信心**：**高**（已由當前 source 隔離重現）；**觸發頻率未在現場量測**。

### F3 — P1：availability 發布失敗後被本機快取永久去重

* **位置**：[src/ha_manager.py:222](../src/ha_manager.py#L222)-[240](../src/ha_manager.py#L240)、[src/bus_master.py:421](../src/bus_master.py#L421)-[423](../src/bus_master.py#L423)、[src/bus_master.py:445](../src/bus_master.py#L445)-[447](../src/bus_master.py#L447)。
* **觸發條件**：設備剛好跨過 ONLINE／OFFLINE 門檻，而該次 retained availability publish 回非零 `rc`。
* **為何會炸**：`set_availability()` 在 [src/ha_manager.py:235](../src/ha_manager.py#L235) 先將 `_availability_cache` 改成目標值，再於 [238](../src/ha_manager.py#L238)-[240](../src/ha_manager.py#L240) 忽略 `_safe_publish()` 的 `False`。同值的下一次狀態轉換呼叫會在 [223](../src/ha_manager.py#L223)-[224](../src/ha_manager.py#L224) 被直接 return，不再嘗試發布。
* **後果**：設備可能已離線而 HA 繼續顯示可用，或已恢復而 HA 繼續顯示不可用。若 MQTT 連線沒有再觸發 `_on_mqtt_connected()`，這個錯誤會維持到反向狀態轉換或程序重啟。
* **可察覺性**：有一次 `publish rc=...` WARNING，之後的被去重不再有 log；scheduler 內部狀態與 HA 顯示永久分叉。
* **隔離證據**：假 MQTT 固定回 `rc=4` 時，第一次 `set_availability(True)` 已將 cache 設為 `True`；第二次同樣呼叫沒有新增 publish（`calls_first=1, calls_after_second=1`）。
* **信心**：**高**（已由當前 source 隔離重現）；**現場是否曾落在這個瞬間未知**。

### F4 — P2：Discovery 發布失敗卻被鎖成「已送完」，HA 實體可能缺件

* **位置**：[src/ha_manager.py:118](../src/ha_manager.py#L118)-[164](../src/ha_manager.py#L164)、[src/ha_manager.py:195](../src/ha_manager.py#L195)-[196](../src/ha_manager.py#L196)、[src/main.py:400](../src/main.py#L400)-[409](../src/main.py#L409)。
* **觸發條件**：連線／重連時的 Discovery flood 中，任一 retained config publish 回非零 `rc`。這可發生於本機 Paho 送出佇列已滿或 client 暫時不可用。
* **為何會炸**：第一次 `send_discovery()` 在 [124](../src/ha_manager.py#L124)-[125](../src/ha_manager.py#L125) 先設 `_discovery_sent=True`，不管後續多個 `_safe_publish()` 是否回 `False`，最後仍在 [164](../src/ha_manager.py#L164) 記錄「Discovery 完成」。下一次正常呼叫在 [119](../src/ha_manager.py#L119)-[120](../src/ha_manager.py#L120) 直接 return。
* **後果**：HA 可能只建立一部分實體或完全沒有該設備實體；網關本機卻認定 Discovery 已送出。只有下一次 MQTT reconnect（會 reset latch）或程序重啟才會重試。
* **可察覺性**：個別 topic 有 `publish rc=...` WARNING，但摘要明確印「完成」，且沒有一個失敗計數或重送排程。
* **隔離證據**：假 MQTT 回 `rc=4` 後，第一次 Discovery 只有一個 publish；第二次呼叫仍是同一個 publish count，但 `_discovery_sent=True`。
* **信心**：**高**（已由當前 source 隔離重現）；正常啟動的四台裝置約 200 則 Discovery 未必足以填滿 1000 筆 Paho 上限，故**現場發生機率中等，非已觀察事實**。

### F5 — P2：寫入已 verify 成功，state 卻可在 200 ms 節流窗被無聲吞掉

* **位置**：[src/ha_manager.py:213](../src/ha_manager.py#L213)-[220](../src/ha_manager.py#L220)、[src/bus_master.py:302](../src/bus_master.py#L302)-[306](../src/bus_master.py#L306)。
* **觸發條件**：HA 下發寫入，設備 ACK 與 verify read 均成功，但 verify result 的 `publish_state()` 距上次 state publish 少於 0.2 秒。這可發生在輪詢剛發布完 state、使用者立刻操作 number／switch，寫入優先權又使 verify 緊接執行時。
* **為何會炸**：`publish_state()` 已把新值寫入 `_state_cache`（[213](../src/ha_manager.py#L213)），接著在節流分支 [215](../src/ha_manager.py#L215)-[217](../src/ha_manager.py#L217) 無 log 回 `False`。寫入路徑不檢查返回值，仍在 [305](../src/bus_master.py#L305) 印「寫入驗證成功」。
* **後果**：設備確實改了、scheduler 也宣告驗證成功，但 HA 不會在此交易收到新 state；目前設定下一次正常輪詢約 6 秒後才有機會補送快取。若這段期間設備離線，HA 會維持舊值直到重新有成功 state。
* **可察覺性**：**無 log**；目前 `profile/config.yaml` 是 `INFO`，操作者只會看到寫入成功，卻看不到本次 state 沒送出。
* **隔離證據**：連續呼叫 `publish_state({'setpoint': 1})`、`publish_state({'setpoint': 2})` 的結果是 `True`、`False`；MQTT 實際只收到一筆，快取已是 `2`。
* **信心**：**高**（已由當前 source 隔離重現）；是否剛好命中 200 ms 視現場操作時序，故**不是持續性故障**。

## 第①題裁決

**FAIL（5 項）**。

不是南北向資料流的所有路徑都壞；設備 I/O、封包 decode、command 格式錯誤與 queue overrun 都已有可見告警。真正仍會讓上層誤判的洞集中在 MQTT acknowledgement／publish return contract：訂閱沒有 broker acceptance 證據，state／availability／Discovery 的 MQTT 失敗沒有被上游成功狀態正確採納。

本報告刻意不提修法、不提重構，避免第①題的敵對證據混入施工方案。下一題應另開審查，不應以本報告推定其結論。
