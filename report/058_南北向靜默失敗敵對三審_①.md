- 日期：2026-08-15
- 審查角色：敵對審查者；目標是找出「程式自己以為做完、HA 實際不知道」的斷點。
- 依據：目前 working tree（HEAD `1f38096`，含未提交修改），不採信舊報告的結論。
- 本次不改 production code、不重啟、不連現場設備。

## 白話結論（給非工程師）

把這套系統想成一個翻譯員：南邊設備回話後，翻譯員要把內容交給 HA；HA 下命令後，翻譯員要真的把命令送到設備。

這次重新檢查後，**先前最危險的幾個洞已經不在目前程式裡**：設備資料發布失敗、設備上下線通知失敗、MQTT 訂閱被拒絕、以及大多數錯誤指令，現在都會留下 WARNING/ERROR，關鍵狀態也會重試。

但仍有一個目前 active 路徑的真洞：**MQTT 剛重新連上時，網關自己的「我在線」公告如果被本機 MQTT 佇列拒絕，程式完全不檢查，也不記錄。**HA 的每顆設備都依賴這一句公告；因此四台設備即使都讀得到，HA 仍可能全部顯示 unavailable。

另外還有兩類「重連後只試一次」與 QoS0 平信的缺口；它們不是 Modbus 壞掉，而是資料已到網關、最後一段交給 HA 時沒有完成保證。監聽（listen）程式尚有兩個靜默吞資料分支，但目前 `profile/config.yaml` 沒有任何 listen 設備，故不是這台正在跑的四台 Solis 的即時觸發路徑。

## 範圍與資料流

目前設定：4 台 `mode: active`、`driver.type: tcp`、UID 1–4、`poll_interval: 6`；沒有 `mode: listen`。

主動北向：`driver.read()` → `adapter.decode()` → `BusMasterScheduler._process_poll()` → `HAManager.publish_state()` → MQTT state → HA。

主動南向：MQTT callback → `EdgeGateway._mqtt_consumer_task()` → `BusMasterScheduler.submit_write()` → `driver.write()` → verify read → MQTT state → HA。

## F1 — Gateway retained `online` 發布失敗被完全忽略

- 嚴重度：P1
- 程式事實信心：高
- 現場觸發機率：中低；須 MQTT client 在 `on_connect` 回呼期間回傳非零 publish rc，例如 QoS1 佇列已滿。
- 位置：`src/main.py:375`、`src/main.py:377`；受影響的 HA availability 契約在 `src/ha_manager.py:364-368`。

### 觸發條件

1. MQTT 剛連上，執行 `_on_mqtt_connected()`。
2. `self.mqtt_client.publish(..., qos=1, retain=True)` 對 gateway Discovery 或 `py_ginlong/status=online` 回傳 `rc != 0`（本 client 設有 1000 筆 QoS 佇列上限）。
3. 兩個回傳物件都在 `main.py:375-377` 被直接丟棄。

`RobustMQTTClient.publish()` 只有在 Python 例外時才自己記錄；「Paho 正常回傳、但 rc 非零」不會被它記錄（`src/mqtt_client.py:91-97`）。

### 會怎麼炸

設備 Discovery payload 指定 `gateway_status_topic` 和 `device_status_topic` 都必須 online（`availability_mode: all`）。若 broker 的 retained gateway status 是 offline，或 broker 重啟後該 retained 狀態尚未建立，這一次 gateway `online` 被拒絕就會讓 **四台設備的所有 HA entity 都維持 unavailable**。

南邊實際輪詢仍會成功、每台 device status 也可能是 online；程式沒有例外、沒有 WARNING/ERROR、health payload 也沒有 gateway status publish failure 欄位。操作者只會在 HA 看見「全灰」，卻找不到對應日誌。

這是「實際會發生」的條件式缺陷，不是 CRC 或設備協定猜想；其前提是 MQTT publish 回傳非零 rc。是否剛好碰到佇列滿，屬外部負載條件，故現場機率標為中低。

## F2 — 重連補送失敗後，外層仍宣告完成，且沒有下一次自動重試

- 嚴重度：P2
- 程式事實信心：高（隔離測試已證明）
- 現場觸發機率：低到中；須某一則 retained publish 在重連窗口回傳非零 rc。
- 位置：`src/ha_manager.py:123-135`、`src/ha_manager.py:164-236`、`src/main.py:409-416`。

### 觸發條件

MQTT 重連後，某設備的 Discovery 或其 cached availability 補送失敗：

- `send_discovery()` 會在 `src/ha_manager.py:228-233` 印 ERROR 並保持 discovery latch 解鎖；
- `republish_availability()` 在 `src/ha_manager.py:133-135` 直接丟棄 `_safe_publish()` 的 bool；
- 兩個函式均不回傳成功／失敗給呼叫端；
- `_staggered_discovery()` 隨後仍在 `src/main.py:413` 印「UID 已送出」，並在 `:416-417` 印「全部送出完畢」。

程式註解本身也承認 Discovery 的下一次重送只靠「下一次 MQTT 重連」（`src/ha_manager.py:173-175`）；單次失敗後不會在已連線狀態自行補送。

### 會怎麼炸

Discovery 失敗時，對應 HA entity 可能不存在；availability 補送失敗時，HA 可保留舊的 offline/online 值。低層有 ERROR/WARNING，所以這不是 F1 那種全黑洞；但**上層運行日誌明確報成功，操作者若只看 Gateway 的分批派送摘要會得到相反結論**。

在 broker 已恢復、但那一次 publish 被短暫拒絕後，系統會持續正常輪詢，卻沒有新的 retained 補送觸發。必須再斷線重連，或設備走到另一個 availability 狀態轉換，才可能自行補正。

### 隔離證據

以 fake MQTT 讓第一次 `set_availability(True)` 成功、下一次 `republish_availability()` 回傳 rc=1：

```
republish_failure_is_not_returned_or_retried None True 2
```

也以 fake MQTT 讓 Discovery 第一則失敗：第一次後 `_discovery_sent=False`，第二次手動呼叫才成功。這證明 latch 已修好；但同時證明「沒有外部下一次呼叫」時，不會自己補送。

## F3 — state payload 使用 QoS0，`True` 只代表本機收件匣接受，不代表 HA 收到

- 嚴重度：P2
- 程式事實信心：高
- 現場觸發機率：中；需 publish 已入本機 client、但 socket 在真正送出前中斷。
- 位置：`src/ha_manager.py:142-155`、`src/ha_manager.py:278-300`、`src/bus_master.py:437-447`。

### 觸發條件

任一正常輪詢或 write verify 後，`publish_state()` 用 `qos=0` 發 state（`src/ha_manager.py:300`）。`_safe_publish()` 對 `rc == 0` 就回 True（`:150-155`）。QoS0 沒有 broker PUBACK，因此這個 True 只證明 Paho 接受本機送件，**不能證明 broker 或 HA 收到**。

若 TCP 在本機入列後、實際 socket write 前後斷掉，該狀態包沒有傳送確認、沒有重傳、也不會計入 `state_publish_failures`；因為 BusMaster 已取得 True，會把本輪視為已送出。

### 會怎麼炸

目前 active 裝置每 6 秒仍會再輪詢，且 state topic 每次帶整個快取；所以 broker 恢復後通常會在下一輪補正，這不是「永久遺失」。但在那個窗口裡：設備可能已完成寫入，HA 仍顯示舊值；程式把它當成功，只會留下通用的 MQTT disconnect 訊息，沒有 UID、key 或遺失 state 的證據。

隔離測試也確認 `publish_state()` 在 fake client 回 rc=0 時直接回 True，且傳遞 `qos=0`：

```
qos0_publish_returns_true_from_local_rc 1 0
```

這是 MQTT QoS0 的協定性限制，不是 Modbus 解包故障；是否改成可確認送達，是對外流量／語意決策，這份敵對審查不擅自要求重構。

## F4 — listen 模式的節流仍可能吞掉「最後一幀」狀態

- 嚴重度：P2（未啟用路徑）
- 程式事實信心：高
- 現場觸發機率：目前為 0；設定檔沒有 `mode: listen`。若日後啟用，為中。
- 位置：`src/ha_manager.py:293-300`、`src/listen_master.py:411-419`。

### 觸發條件

listen 收到兩個不同狀態幀，第二個到達時間距離前一次 state publish 小於 200ms；`publish_state()` 在 `src/ha_manager.py:295-297` 回 False，不記日誌。Listen 端只在 `src/listen_master.py:412-419` 撤回自己的 diff cache，也不記日誌，並把重試寄望於「下一個有效封包」。

若第二個封包剛好是串流結束前最後一幀（例如告警 ON 後設備停止發報），就沒有下一幀可促成補送。

### 會怎麼炸

HA 永遠收不到最後改變的值；設備稍後只會因 timeout 變 unavailable，日誌沒有指出「有效封包到達但 state 被節流丟掉」。使用者可能只看到舊告警值或 unavailable，無法區分是設備沒送還是 Gateway 吞掉。

這不是目前四台 active Solis 的路徑；active polling 每 6 秒有下一輪完整 state，因此不可把它誤報成現場既發事故。

## F5 — listen 對超過 256 字元的值直接丟棄，不留紀錄

- 嚴重度：P2（未啟用路徑）
- 程式事實信心：高
- 現場觸發機率：目前為 0；日後 adapter 產生長診斷字串時才會觸發。
- 位置：`src/listen_master.py:348-355`。

### 觸發條件與後果

`adapter.feed()` 成功回傳 dict，但某值是長度大於 256 的 str，`src/listen_master.py:350-351` 直接 `continue`，沒有任何 log。若那是該幀唯一欄位，`clean_data` 變空，`:354-355` 不會呼叫 `_process_valid_frame()`。

換句話說，串口/TCP 確實收到並成功解碼合法封包，但 Gateway 對 HA 完全不發布，也不把設備視為已看見；最後只可能在離線計時器後顯示 unavailable。使用者察覺得到「沒資料」，但不知道是長字串防護把資料丟掉。
